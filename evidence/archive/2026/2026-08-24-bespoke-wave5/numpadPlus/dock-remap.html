The hint line is instructional copy in a TRANSIENT MODE, not resting text. It is the same class as midiclock's pre-connect hint and its access-failure message, both of which wave 4 kept. At rest it is present and empty — deliberately, because the probe's expect: 'changed' is a comparison and an element that appears on click is not something to compare against.
A left-click on a key cap does NOTHING today, and that is why this state had to be designed. ShellPanelProbe.action is 'click' | 'drag' — there is no right-click action — and NumpadPlusCard.svelte:296-307 gives the cap oncontextmenu and no onclick. ShellPanelCell.probe is a REQUIRED field (shell-cells.ts:395, non-optional) enforced over every promoted face by shell-cells.test.ts, so an inert cap cannot be a face cell. Left-click begins the remap — one click instead of two for the common action — and right-click keeps the full menu.
⚠ The sweep must not be left holding the keyboard. faces-parity clicks and moves on. A panel left listening would capture the sweep's NEXT keystroke and silently rebind a key — a test that mutates the fixture it is measuring, which is the instrument-bug class this repo keeps finding. The panel cancels on pointerdown outside itself, on blur and on Esc, and M4 makes "a faces-parity pass leaves node.data.keymap byte-identical" a permanent leg of numpadPlus-face-model.test.ts.

the probe, and why it is text

'numpad-key-{n}': {
  kind: 'panel',
  label: 'key map',
  component: NumpadKeymapPanel,
  minWidth: 208,
  probe: {
    testid: 'numpad-key-0',
    action: 'click',
    effect: { kind: 'text',
              testid: 'numpad-key-hint',
              expect: 'changed' },
  },
}

Beginning a remap writes nothing to the graph — remapSemitone is component state — so a data probe would be RED on a perfectly live cap. shell-cells.ts:373-381 says text exists for exactly this, and requires the named element to differ from the clicked one, so a cap that only relabels itself cannot pass.

ONE family, not two

The card emits two prefixes for one control kind: numpad-key-{st} for semitones 0–11 and numpad-octkey-{act} for the two octave actions. The DEF does not agree — DEFAULT_KEYMAP is ONE fourteen-entry map and OCTAVE_UP_ACTION = 12 / OCTAVE_DOWN_ACTION = 13 are described in the def's own comment as remappable keys keyed by sentinel values outside the note range.

So the split is a card artefact. One family, members numpad-key-0 … numpad-key-13 — one contract line instead of two, and the card's prefix is unified in the same PR.

⚠ That breaks numpad-plus.spec.ts:134-135 and :151, which are fixed alongside.

⚠ this is NOT keyboard-a11y work

The standing owner ruling forbids keyboard-navigation accessibility: focus rings, tab order, arrow traversal, roving tabindex. None of that appears in this spec and none may be added.

What IS in scope is the module's own instrument: a document-level capturing keydown listener that turns keypad presses into MIDI notes, installed in the FACTORY (numpad-plus.ts:604-683), not the card — so promotion does not touch it. Separating those two is the difference between preserving a feature and doing forbidden work.
