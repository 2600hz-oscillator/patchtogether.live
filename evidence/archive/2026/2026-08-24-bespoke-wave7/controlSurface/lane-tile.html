THE REFUSAL, IN ONE SENTENCE: a single group box (174 px) nominally fits inside the tile (192 px) — and no seam can put it there. fullViewBody is dock-only, enforced by dockFullViewHeadPlan (“a 192 px lane tile cannot carry a module surface”, matrixmix/shell-extension.ts:53-58), and the glyph slot's props carry no nodeId, so every instance of a module draws the identical picture — a per-node binding set is unreachable through it. So promotion trades four columns of live knobs on the canvas for a 192 px tile and a dock open, on a module built so you would not have to hunt. That is #1974 (joystick) verbatim.

WHAT WOULD LIFT IT — a LANE-TIER extension slot (spec.md §12). Call it laneBody: the same contract as fullViewBody, rendered at the full LOD tier, with the tile's uniform size relaxed for occupants that declare one. ⚠ And a third item a PR would forget: EXTENSION_BODY_ROLES's population is derived from fullViewBody: presence (face-rack-status-source.test.ts:100-115), so it would go blind to a laneBody unless widened. It serves five modules — controlSurface, electraControl, launchpadControlLeft, clipplayer, push2Control. Not proposed as part of any face PR; recorded as the named blocker.
AND IT IS NOT THE ONLY BLOCKER. Even with a laneBody, authoring a face is RED on face-migration-inventory.test.ts: leg :229 forces the entry to generic-face, and leg :226-248 refuses generic-face for any module whose legacy card mounts typed entry — which ControlSurfaceCard.svelte:364-376 does, and promotion does not remove that card. ⚠ Wave 6 §5.2's remedy (“empty the blockers array”) does not help: the leg continues out of the generic-face branch before it reads that array.
