## Executive summary
SHIP the per-clip / per-lane automation direction — it is proven prior art, not speculation (Ableton unlinked clip envelopes; Bitwig 6 pulled automation OUT of note clips into per-parameter clips and names the owner's exact "1/4-speed-over-4-bars" case "polymetric automation"). But make ONE architectural correction and solve ONE hazard before building. Correction: do NOT embed tracks on the NoteClipRecord value (the owner's literal "1:1 on the note clip"); store automation as a SEPARATE sibling object keyed by the same stride-64 clipIndex. Embedding is the exact coupling both DAWs deliberately avoid, and in THIS codebase it reintroduces multiplayer note-clobber and silent automation-drop that the current separate-clip model structurally prevents — a regression dressed as a port. Hazard: the param-jump problem the owner fears is real, unsolved in both DAWs, and the current branch has ZERO of the mitigations (scheduleParam never cancels; no restore path anywhere). The per-clip model makes it WORSE (clip-switch becomes a per-control jump event × mapped controls) unless a layered hold-last-value + glide + soft-takeover policy ships first. Net: keep the excellent pure engine cores, re-home storage to a sibling keyed structure, ship the jump policy as Phase 0 on today's code, make record state per-lane, and accept that ASSIGN stays card-side while ARM/VIEW/EDIT become genuinely launchpad-first on all three controllers.

## Ranked findings (5 BLOCKERs)
1. BLOCKER — storage: embedding tracks on the NoteClipRecord value collides with two hard existing constraints. (a) coerceClipRecord('note') rebuilds a clip from {kind,steps,lengthSteps,root,loop,scale,div,color,name,gain} with NO tracks field, so ANY note edit that round-trips coerce (toggle a note, change length/scale, paste) silently drops the recorded automation. (b) Durable writes are whole-clip PLAIN reassigns into one d.clips[key]; sharing that key between notes and automation makes a peer's per-wrap automation commit and a peer's note edit last-writer-wins on the SAME key → note data lost during recording. Both are IMPOSSIBLE today because automation is a different kind at a different cell. FIX: sibling keyed object d.auto[clipIndex], nested Y.Map per target.
2. BLOCKER — param-jump: scheduleParam (engine.ts:603) only piles setValueAtTime/linearRamp onto the AudioParam; it NEVER calls cancelScheduledValues/cancelAndHoldAtTime, and there is NO restore path when a lane stops (clipplayer.ts:966 just `continue`s). So every clip-switch is either a hard step to the new clip's step-0 value or an indefinite FREEZE at the old clip's last value plus a 200ms ghost ramp tail. In the per-clip model this fires per mapped control on every launch — the owner's hazard becomes the common path, not an edge case.
3. BLOCKER — record state is per-PLAYER not per-lane: one data.automation={arm,recorderId,clip}, one controller pass/window, one automationRecordTarget. It cannot record two lanes concurrently (the owner's model demands it) and it silently corrupts on a mid-record clip switch: applyLaneQueued swaps ln.active at a wrap, recordTick stops matching, the pass is neither punched-out nor cleared, and disarm writes the partial into the STALE target; a shorter swapped-in clip drops all tail events. The queued-launch-lands-on-wrap race writes clip A's pass into clip B.
4. BLOCKER — launchpad-first is currently false for 4 of 5 lifecycle stages. Only ARM exists on hardware, and only on the SINGLE unit in Control view (CTRL_AUTO_ARM_COL at 2,6 in handleSingleControl); the dual-Launchpad rig (the config with the MOST surface) and monome have ZERO hardware automation. ASSIGN and EDIT are mouse-only; there is no Automation View at all (the note editor edits notes only). The signature div/length workflow cannot be set from hardware.
5. BLOCKER — touch-override releases at the LOOP WRAP, not on physical release, and notifyAutomationTouch fires only on pointerdown. A knob gesture spanning a wrap loses suspension mid-drag: the param is yanked to the just-recorded envelope while the hand is still holding it, live setParam then fights scheduled playback, and the held value stops being sampled so the second loop records nothing. Live bug on the current branch.
6. MAJOR — no whole-pass position cue on long automation: the only surface signal is a 4-beat YYRR pre-roll computed WRAP-relative, so on the coprime lengths the card advertises as a feature it pulses OFF the song beat and actively misleads. A performer recording a 4-bar sweep cannot tell bar 2 from bar 3.
7. MAJOR — full-loop overdub replaces a touched track's ENTIRE [0,len) window from one brief touch (commitPass → mergeAutomationOverdub window [0,len)). On automation longer than the note clip, a one-beat spot-fix in bar 3 collapses bars 1-2 to a straight seed→touch ramp and flattens bar 4 — the opposite of Ableton/Bitwig TOUCH semantics.
8. MAJOR — phase alignment is not guaranteed: note and automation playheads are independent per-lane accumulators anchored to their own launch instants with no re-anchoring, and advance via repeated FP += that drift by ULPs. The signature commensurate case (1/4-speed, same length) only lands on note-loop boundaries if launched at exactly the right instant; late-launch smears 'variation' across bar lines permanently.
9. MAJOR — multiplayer resting-value divergence: playback writes only the transient AudioParam + local knobValues, never the Y.Doc, so on stop each peer freezes the param at whatever ITS audio phase last scheduled. Peers hear different mixes with no reconciliation; a reload snaps to a third value. No single-user DAW has this failure mode.
10. MAJOR — no lease on the single-writer recorder: arm+recorderId are synced but nothing clears them on tab-close/crash. A dead recorder leaves every peer showing the red pulse + countdown forever while nobody captures, and the in-flight take is lost (disarm runs only on the recorder client). A second armer silently steals the role.
11. MAJOR — discrete/stepped params get no authored value at map-time, so under per-clip a selector frozen at one clip's value stays wrong on any clip that doesn't automate it (Ableton's 'unspecified discrete param' gotcha, made permanent by the no-restore design).
12. MAJOR — hot-path cost: readClip→coerceClipRecord→coerceAutomationTrack deep-clones + step-SORTS every event array every ~25ms tick with no cross-tick cache; embedding on the note clip multiplies this by every playing lane. The tick already documents that per-step coerce made the fast-clock scheduler STALL lanes (saw -1); this reintroduces it at per-lane granularity.
13. MINOR — arranger vs per-clip collide on one card with two overlapping record buttons (red ● records launches, teal ◉ records knobs); arbitrary-length per-clip automation silently becomes a de-facto arrangement no 8x8 grid can navigate. Undo is per-wrap not per-take; event cap tail-truncates silently; snapshot/audio clip interaction with automation is unspecified.

## Recommended architecture
DATA MODEL — keep the 1:1 note↔automation association the owner wants, but as a SEPARATE keyed object, never a field on the note clip. Add a sibling sparse map d.auto keyed by the SAME flat stride-64 clipIndex(slot,lane)=lane*64+slot as the note clip, so 'each note clip implicitly has an automation object' is expressed as a parallel key, not co-storage. This gives disjoint CRDT/merge/undo scopes: note reassigns and automation commits touch different keys → no lost-update; coerceClipRecord('note') never has a tracks field to drop. Store each object's tracks as a NESTED Y.Map keyed by target (nodeId:paramId) whose value is the event list, so a record commit mutates ONLY the touched track's events — kill the whole-clip plain reassign on the recording hot path. Carry over WHOLESALE (storage-agnostic, already pure + unit-tested): RecordGate decimation, QuantizedRecordWindow, stepRampPoints, mergeAutomationOverdub, automationValueAt/LinearAt, trackInterp, coerceAutomationTrack/Event, the AutomationController touch-gate, the automation-touch.ts cross-wire, the transient scheduleParam/setDisplayParam seams, curve-aware readNorm/drive. DELETE: AutomationClipRecord 'kind', data.automation.clip pointer, ＋AUTO/defaultAutomationClip, DEFAULT_AUTOMATION_STEPS/DIV, automationClipDisplay, and the activeClip.kind==='automation' branch that REPLACES emitLaneStep (a note clip must now emit notes AND drive its own tracks in the same step loop).

OWNERSHIP — resolve the owner's clip-vs-lane contradiction decisively: length+div is a PER-CLIP-AUTOMATION property (matches the existing AutomationClipRecord fields, matches Ableton/Bitwig). Re-cast 'the automation LANE' as (a) a per-lane DEFAULT that stamps length+div into each new clip's automation object, and (b) a VIEW/mode. This makes the normal case — two differently-sized note clips sharing one lane — behave correctly: each carries its own automation length rather than one lane setting misapplying to both.

TIMING/LENGTH MODEL — decouple automation length+div from the note clip (Ableton unlinked envelope / Bitwig Custom Loop; proven, this IS the owner's feature). Express it as a musical RATIO to the note clip (½× 1× 2× 4× length) plus an explicit Linked / Custom-Loop lock; keep raw length-in-steps + div as an advanced unlinked override. PHASE: derive BOTH the note and automation playheads from a COMMON transport-relative origin (the shared RST/transport anchor the card already claims for rates), not each lane's launch instant, and compute wrap times as origin + n·laneDur (closed form, NOT repeated FP +=), so a commensurate automation loop lands deterministically on note-loop boundaries and coprime lengths drift predictably rather than by accumulated ULPs. Surface whether a given (len,div) pair is commensurate or drifting so the user knows the regime. RECORD state becomes PER-LANE: a QuantizedRecordWindow + pass + commit-target per lane, driven by that lane's LIVE active clip each tick; latch the commit target to the clip instance playing at pass-START and commit to THAT latched (slot,lane) BEFORE applyLaneQueued swaps, so a queued launch on the wrap commits to the outgoing clip. Keep the global recorderId as the single-WRITER gate, but lease it against awareness/presence (clear on disconnect; stale id → treat unarmed).

## Param-jump policy (layered — Phase 0 on todays code)
DEFAULT POLICY (beats both DAWs; ship as Phase 0 on today's code BEFORE the rewrite because it is engine-level and carries over wholesale). A LAYERED stack — no single mechanism covers all three seams (clip-switch, loop-wrap, arm/disarm):

1. HOLD-LAST-VALUE on automation-stop/absence — NEVER snap to default/zero (that is the exact Bitwig-launcher complaint users beg to disable). Implement deliberately: on any automation-stop for a param call param.cancelAndHoldAtTime(ctx.currentTime) so the 200ms lookahead ghost tail dies and the value is pinned, not left drifting or frozen-by-accident.

2. DETERMINISTIC resting value (multiplayer-safe) — the hold value must be a PURE function of clip data + stop-step (automationLinearAt at the stop step), identical on every peer, so collaborators converge by construction rather than freezing at whichever peer's audio phase fired last. Do NOT persist it via a live-store write (honors the CV-modulation-no-store-write rule); it is a pure recompute.

3. ALWAYS-ON de-zipper glide — a per-lane 5–30ms linearRamp across every unavoidable seam. Loop-wrap: make the last-step→step-0 transition a short linearRamp instead of the current hard setValueAtTime (stepRampPoints step-0 anchor with ramp:false) — with the owner's different-length/coprime loops the endpoints essentially NEVER align, so a wrap click is otherwise the norm. Clip-switch INTO a clip that automates the param: ramp from the held value to the new step-0 value, never setValueAtTime. This turns every legitimate discontinuity into an inaudible ramp.

4. cancelAndHoldAtTime on TOUCH as well as stop — the instant a hand grabs a mapped param, truncate the scheduled tail at its current value so manual input isn't overridden by queued events for up to 200ms ('knob fights back').

5. Override releases on physical touch-END (pointerup / CC-idle timeout / Electra release), NOT the loop wrap. Fire notifyAutomationTouch on down and hold a 'grabbed' flag until up so a wrap can't clear an active gesture; on release apply a short return-to-baseline glide (Deluge's ~1s reference), don't hold to the wrap.

6. Soft-takeover when a mapped control is grabbed on an armed, playing lane — expose Ableton's Takeover menu (None / Pick-Up / Value-Scaling); default VALUE-SCALING (converges as you move) for performance, Pick-Up for precision. Automation-owns-the-param (clip-switch/loop) uses jump-with-glide, NOT pickup (playback must stay deterministic).

7. Author-a-value at map-time — on right-click→map (and auto-capture), stamp the control's CURRENT value as one breakpoint into EVERY existing clip in that lane and into new clips, so there is never an 'unspecified hole' (fixes discrete-param permanent-wrong-value and gives the glide a defined target).

8. Per-mapping ABSOLUTE vs bipolar-OFFSET switch — OFFSET-around-the-manual-base is the strongest STRUCTURAL cure: on a clip switch the base stays put and only a small offset changes, so a wild jump is impossible. This same switch governs the modular-specific CV-cable case (a third writer summing on inputs[paramId].param): absolute automation owns the intrinsic and treats CV as offset, or route to distinct summing stages.

9. Re-sync to written automation is an EXPLICIT gesture (re-launch the note clip = re-enable, or the override dot), NEVER automatic — Ableton's sticky-override model.

Plus a per-segment STEP-vs-SLIDE toggle (Elektron slide / Deluge interpolation) including at the wrap seam, so the user decides authoring-time whether a transition snaps or glides.

## Launchpad-first UX
Reframe 'launchpad-first' honestly: perform + ARM + VIEW + EDIT + read-state from hardware; ASSIGN (target-picking) stays CARD-SIDE by necessity — the params live on OTHER module cards, not on the grid, and the Mini has no encoders, so Push's per-encoder colocated model CANNOT be ported. State this explicitly so 'end-to-end launchpad' means perform+edit, not map.

ARM (invariant): a first-class automation ARM reachable in the DEFAULT view of EVERY bound controller — single, DUAL/pair, and monome — all writing the same data.automation.arm/recorderId. Today it exists only on the single unit in Control view (rDeckPad has no automation action; monome greps empty). Add a dedicated pad/reclaimed top-row CC on the pair R-deck and a monome pad; add a test asserting a hardware arm path exists for single, pair, and monome. Surface arm/countdown in a PERSISTENT element visible across ALL views (tint the permanent top-row transport or a fixed status pad while armed) so record state is never hidden behind a mode.

VIEW/EDIT — a dedicated Automation VIEW mode (a mode flip like the note editor), scoped to ONE lane/clip at a time and PAGED between lanes explicitly; do NOT try to render 8 lanes' automation concurrently on the static matrix (extend AutomationRenderState to per-lane first). Inside it, adopt the Deluge Automation View idiom wholesale (the most launchpad-native automation editor in the field, needs no encoders): column = time step, row = value bar-graph (bottom=min, top=max), single-pad press paints a value, HOLD pad A + press pad B draws a linearly-interpolated ramp across the columns between, an interpolation on/off toggle switches ramp vs step. Use the RGB advantage: tint each lane in ITS lane color, show value via lit height + brightness, and light an overview marking which params are automated. 8 rows is coarse (~1/8) — add a fine mode (shift-zoom the 8 rows onto a sub-range) and top-row CC ± nudge for delta entry (relative input is the true no-jump escape hatch). Add a hold-pad-to-scope-a-step + nudge p-lock path so a single point of a long take is fixable without re-performing the whole pass.

DIV/LENGTH (signature workflow) settable IN the Automation View: reuse the RATE color ramp for the automation div and the LEN page's block/step ruler for the automation length, plus a Linked/Custom-Loop toggle and a ½×/1×/2×/4× ratio quick-pick, so '1/4-speed same-length' is a couple of pad taps.

FEEDBACK — the owner's 'thin colored lane-border on the control name' is the card analog of Push's gray override dot; give it a hardware projection: dedicate the scene column (or a strip) in the Automation View to per-lane read/armed/overriding state — reading = lane color solid, overriding-by-hand = lane color blink, armed = red. Add a whole-pass PROGRESS indicator (a sweeping lit column / position-in-loop 0..1) so a long take is legible, and quantize any beat-flash to the SONG beat grid, not the wrap-relative YYRR that misleads on coprime lengths. MONOME (monochrome): DROP color-identity as the primary cue — use a fixed lane-per-row map + brightness for read/override, and keep its automation story as global-ARM overdub + per-step grid draw (no color, no encoders).

RECORD spine: keep global ARM + touch-gated overdub (matches Push's single red Automate + touch-sensitive write), but expose an EXPLICIT Latch/Touch/Write mode selector (Bitwig) since a hardware surface has no mouse-vs-knob distinction to key behavior off, and add the deterministic hold-pad-set-value STEP path since the Mini can't smoothly capture a knob sweep on-device.

## Per-clip vs arranger
Build PER-CLIP automation FIRST and make it the PRIMARY model — it is both the launchpad-first core (automation loops identically on every pad launch, exactly matching clip-launching) and the model both market leaders lead with. Do NOT block it on the arranger. Treat arranger-mode automation as a strictly LATER, screen-only layer: the Launchpad cannot scrub song time, so a song-timeline automation editor is inherently a mouse/screen surface, and per-clip automation should OVERRIDE arranger automation while a clip plays (Ableton/Bitwig session-overrides-timeline semantics). Design the promote/flatten seam NOW even though you don't build it: store tracks in a form that can be consolidated onto an arrangement lane later (Ableton prints/consolidates session envelopes into arrangement automation) — this is free if storage is the sibling keyed object above. Two concrete guardrails so per-clip doesn't quietly BECOME the arranger: (1) cap sanctioned per-clip automation multiples to small musical ratios (≤~4×) behind the explicit Linked/Custom-Loop lock, so a clip can't silently grow into a 32-bar de-facto arrangement that no 8x8 grid or LED countdown can make navigable; (2) unify the two record buttons' semantics before they calcify — today the red ● arranger-record captures clip LAUNCHES only and the teal ◉ AUTO captures knob moves, which will confuse anyone expecting arranger-record to also capture automation across the song. Decide that 'record' means the same thing in both modes, with the arranger layer added later.

  - fix: Add a first-class automation ARM to pair mode (a dedicated deck pad or a reclaimed top-row CC on R) and to the monome, writing the same `data.automation.arm`/`recorderId`. Treat 'arm is reachable on every bound controller in its default view' as an invariant with a test that asserts a hardware arm path exists for single, pair, and monome.
- **[blocker]** The proposed per-lane/per-clip model is not expressible on the current single-pointer hardware surface, and there is no free real estate or dedicated automation mode to make it so. The live model is ONE global pointer (`data.automation.clip`), ONE arm flag, ONE `AutomationRenderState`, ONE countdown, ONE arm pad. The owner wants 8 note lanes each carrying an independent automation lane with its own arm, div, length, and curve.
  - fail: Under the per-lane model, lane 2 is overdubbing a cutoff sweep while lane 5's automation is mid-countdown to its own (different-length) wrap and lane 7 is being curve-edited. The hardware can show exactly one of these: one arm pulse, one countdown cell. L (8×8) is the matrix and R is the deck/editor — there are no free pads to hold eight independent per-lane arm/div/length/curve states, and there is no automation MODE to page them into.
  - prior art: The Deluge gives each clip its OWN Automation View that you flip INTO per clip+param — it never tries to render every lane's automation state at once on a static grid. Bitwig relies on a screen. Neither model puts 8 simultaneous per-lane automation states on 64 static pads; the owner's design implicitly requires the mode-switch the current impl lacks.
  - fix: Design a dedicated Automation VIEW (a mode flip, like the note editor) scoped to ONE lane/clip at a time: enter it for the armed/selected lane, show that lane's arm + div + length + curve, and page between lanes explicitly. Do NOT try to surface 8 lanes' automation concurrently on the matrix. Extend `AutomationRenderState` to per-lane before the countdown/arm paint can mean anything in the new model.
- **[blocker]** Two of the five lifecycle stages — ASSIGN (control→lane) and EDIT (the curve) — are mouse-only on every controller, and one of them is structurally un-portable to the grid. Assignment is right-click 'map to automation lane' (a card affordance); there is no Automation View, so the on-grid note editor edits notes only. Deeper: the params being automated live on OTHER module cards, and the Launchpad Mini has no encoders and no parameter readout.
  - fail: A user wants to map 'the wavefolder drive on the synth three cards over' to a lane and draw a ramp — entirely from the grid, mid-set. There is no grid gesture to pick that target (it isn't on the grid), and no grid surface to draw its curve. They must mouse the target card to assign, then mouse again to draw. 'Launchpad-first end-to-end' is false for these two stages.
  - prior art: Push's automation works because its 8 touch-encoders ARE the 8 on-screen params under the pad columns — pick/arm/override all colocate. The Mini has no encoders and the targets aren't on the grid, so that model cannot be ported. The grid CAN host a Deluge-style column=time/row=value curve editor for an ALREADY-mapped param — copy that for EDIT — but target-picking cannot leave the card.
  - fix: Accept and state explicitly that ASSIGN stays card-side (right-click), so 'launchpad-first' means 'perform + edit from hardware', not 'map from hardware'. Then actually build the EDIT stage: a Deluge-style Automation View (single-pad paints a value, hold-A+press-B draws an interpolated ramp) inside the per-lane automation mode from finding 2. Without it, EDIT is mouse-only too and the grid is a launch-and-arm surface, not an automation surface.
- **[major]** The owner's 'thin colored lane-border on the control name' has no launchpad equivalent — hardware automation feedback is binary (arm pad pulses red = globally armed y/n) plus a 4-beat countdown on one cell. There is no way to see WHICH params are mapped, which are currently capturing your touch (touch-gate/override), or their lane color. On monome it is worse: the device is monochrome, so the lane-COLOR identity that the whole mapping design hangs on cannot be shown at all.
  - fail: A user has cutoff, resonance, and drive mapped across lanes 2/3/5. They grab the cutoff knob during playback (touch-suspends that track). On the grid nothing changes — no per-param override indicator exists — so they cannot tell from hardware whether their move is being captured, which lane owns it, or that resonance is still reading its envelope. On monome they additionally cannot tell lanes apart by color at all.
  - prior art: Push shows a per-encoder GRAY override dot for exactly this hand-vs-automation ownership; the Deluge lights an overview page marking which params are automated. The card's colored border is the analog of these — but it has no hardware projection, and the touch/override state the owner explicitly wants is invisible on the grid.
  - fix: In the per-lane Automation View, dedicate a strip or the scene column to a per-lane read/armed/overriding state (e.g. reading = lane color solid, overriding = lane color blink, armed = red), so ownership is legible on hardware. For monome, replace color-identity with position+brightness (a fixed lane-per-row map + brightness for read/override) and stop treating lane color as the primary cue there.
- **[major]** The signature workflow — automation lane at a different clock-multiple and length than the note clip (the 1/4-speed-over-4-bars variation trick) — cannot be set from hardware at all. The RATE row and the LEN page act on the NOTE lane/clip; there is no automation-specific div or length control anywhere on the grid.
  - fail: Mid-jam a user wants the classic move: automation same length as the clip but at 1/4 speed so it evolves over 4 loops. On the grid, cycling RATE changes the note lane's clock and LEN edits the note clip's length — neither touches the automation lane's independent div/length. They must stop and open the card to dial the one workflow the owner calls signature.
  - prior art: Ableton exposes the unlinked envelope's own loop start/length/period in the clip editor; Bitwig exposes 'Custom Loop' length/start on the automation clip. Both make the decoupled length/period a first-class, directly-settable control. The owner's headline feature has no hardware control at all here.
  - fix: Give the per-lane Automation View an explicit div selector (reuse the RATE color ramp) and a length ruler (reuse the LEN page's block/step ruler) scoped to the AUTOMATION lane, plus a Linked/Unlinked toggle. Ensure the 1/4-speed-same-length preset is reachable in a couple of pad taps.
- **[minor]** Automation feedback is view-gated and the stolen automation cell is ambiguous. The countdown/arm paint is only wired into `SingleGridOpts` and `SingleControlOpts`, so it renders in Grid and Control views only; and arming on a single unit forces a flip to Control view, which hides the live clip matrix. The automation clip also occupies a real matrix cell that looks identical to a loaded note clip except during its 4-beat countdown.
  - fail: A user arms automation, then flips to the note editor (or KEYS/Arranger) to tweak the part while it records. They get no countdown and no arm indication in those views — no signal that recording is live or about to wrap. On a single unit, to arm at all they leave Grid and lose sight of which clips are playing. In Grid, the automation cell reads as an ordinary dim-blue loaded clip ~60% of the loop.
  - prior art: Push's Automate button and Ableton's transport arm are always visible regardless of the current editing surface, so record state is never hidden behind a mode. Ableton also visually distinguishes automation from clips rather than parking it in an identical launch cell.
  - fix: Surface arm/countdown state in a persistent element visible across views (e.g. tint the permanent top-row transport or a fixed status pad while armed), and give automation cells a distinct steady tint so they are legible outside the countdown window — or, once per-clip lands, drop the stolen-cell model entirely so the ambiguity disappears.

### data-model-sync-perf — verdict
The MUSICAL direction (per-lane automation with its own clock-multiple + arbitrary length) is sound and prior-art-validated (Ableton unlinked clip envelopes, Bitwig polymetric automation). But the STORAGE decision the owner is reaching for — embed the automation 1:1 on the NoteClipRecord value — is the exact structural choice both market leaders explicitly AVOID (Bitwig 6 pulled automation OUT of note/audio clips into separate per-parameter clips), and in THIS codebase it collides head-on with the two hardest existing constraints: (1) the audio-scheduler tick re-`coerceClipRecord`s the active clip every ~25ms with NO cross-tick cache (clone + O(n log n) sort of every event array), and (2) durable writes are whole-clip PLAIN reassigns into a single `d.clips[key]` — so sharing that key between notes and automation creates lost-updates and silent automation-drop. Recommendation: keep the pure engine cores (they are storage-agnostic and excellent), but DO NOT embed tracks in the NoteClipRecord value. Store each lane's automation as a SEPARATE keyed object (e.g. an `auto` sibling map keyed by the same flat index, or a distinct kind cell) so notes and automation stay independent CRDT/undo/reassign units; add a coerce-ONCE read cache off the hot path (or a precompiled read-only breakpoint view); make record state PER-LANE (the single global `recorderId`/pass/`automationRecordTarget` cannot record two lanes or survive a mid-record clip switch); add explicit phase re-anchoring for commensurate loops; and surface the event cap instead of truncating. The per-clip model can ship first, but only if storage is a separate object, not a field on the note clip.
- **[blocker]** Automation events are re-coerced (deep-cloned + step-SORTED) on the audio-scheduler thread every tick with no cross-tick cache; embedding tracks on the note clip multiplies this by the number of PLAYING lanes and couples note-scheduling latency to automation payload size.
  - fail: clipplayer.ts:973 calls readClip(d0, clipIndex(ln.active, L)) once per active lane per tick; readClip→coerceClipRecord→coerceAutomationTrack runs events.map(coerce).sort().slice() on EVERY call (verified: no memoization; a second readClip at line 1051 re-coerces the pointer clip again). A single automation clip near the 4000-event cap with 16 tracks = 64k events cloned+sorted ~40×/s on the main thread TODAY. Move automation onto the note clip and every one of up to 8 simultaneously-playing note lanes carries that payload, so a modest 3-lane performance with dense sweeps = ~180k events cloned+sorted per tick, 40×/s ≈ 7M event-object allocs/s. The tick already documents (clipplayer.ts:967) that per-step coerce 'made the fast-clock scheduler fall behind and STALL lanes (saw -1)'; this reintroduces that stall at the per-lane granularity and GC-thrashes.
  - prior art: Bitwig 6 stores automation in SEPARATE per-parameter clips precisely so note/audio scheduling is not coupled to automation size; Ableton precompiles clip envelopes into a read-optimized structure and never re-parses the whole envelope per audio block. Neither re-clones+sorts an event array on the DSP callback.
  - fix: Do not embed tracks in the NoteClipRecord value read on the hot path. Coerce/sort ONCE at load/edit into a cached, already-sorted read-view keyed by clip identity+revision, and have the tick read that cache (no per-tick coerce). If automation stays per-clip, store it under a sibling key so the note path can read notes without paying the automation clone.
- **[blocker]** Durable writes are whole-clip PLAIN reassigns into one d.clips[key]; sharing that key between notes and automation causes multiplayer lost-updates AND single-user silent automation-drop, because coerceClipRecord('note') does not carry an embedded tracks field.
  - fail: Two failures. (a) LOST UPDATE: the commit dep (clipplayer.ts:410-423) does d.clips[key] = plainAutomationClip({...rec, tracks}) — a whole-value reassign every wrap. If automation and notes share the key, peer A's per-wrap automation commit (carrying a stale copy of notes read at commit-start) and peer B's note-edit reassign (carrying stale automation) are last-writer-wins on the SAME key → whichever lands second wipes the other. Today automation is a separate kind at a DIFFERENT cell, so note edits and automation commits never touch the same key and this cannot happen. (b) SILENT DROP: coerceClipRecord('note') (clip-types.ts) reconstructs a fresh NoteClipRecord from only {kind,steps,lengthSteps,root,loop,scale?,div?,color?,name?,gain?} — no tracks. The moment tracks live on the note clip, ANY note write that round-trips coerce (toggle a note, change length/scale, paste) rebuilds the clip WITHOUT tracks: user records a filter sweep into clip 3, toggles one note in the piano roll, sweep is gone.
  - prior art: Bitwig's per-parameter automation clip is a distinct object from the note clip — editing notes and editing automation are independent undo/merge units, so neither clobbers the other. Embedding automation on the note-clip value is the coupling both Bitwig and Ableton avoid at the storage layer.
  - fix: Store automation as a SEPARATE keyed object (sibling map d.auto[flatIndex] or a distinct kind cell), never as a field inside the NoteClipRecord value. Then note reassigns and automation commits are disjoint keys (no lost-update), and coerceClipRecord('note') never has an automation field to drop. If it MUST be embedded, coerceClipRecord('note') must carry tracks and every note-write path must be audited to preserve it — a large, error-prone surface.
- **[major]** Record state is per-PLAYER (single data.automation={arm,recorderId,clip}, single controller pass/window, single automationRecordTarget). It cannot record multiple lanes concurrently, and it silently corrupts on a mid-record clip switch.
  - fail: The owner's model = 'mapped params record into the automation of the clip playing in THEIR lane', with controls mapped to different lanes — so arming should record lane 2 AND lane 5 at once. The controller (clip-automation-controller.ts) holds ONE QuantizedRecordWindow, ONE pass Map, ONE passClip; the factory holds ONE automationRecordTarget {slot,lane} set right before recordTick. It physically cannot track two lanes' independent wraps or commit two clips. Worse, mid-record clip switch: the per-lane while-loop (clipplayer.ts:1024) calls applyLaneQueued which swaps ln.active at a loop boundary within the tick; the record block then no longer matches ptr.slot so recordTick is not called, the in-flight pass is neither punched-out nor cleared, and automationRecordTarget holds the OLD clip. On the next disarm, commitPass writes the partial pass into the stale target. If the swapped-in clip has a different lengthSteps, recordTick is fed a new len while the RecordGate holds events at the old-len steps → mergeAutomationOverdub clamps windowEnd to the new len and drops/mis-merges every event past it. Concrete: overdub into a 64-step clip, a queued launch swaps to a 16-step clip, tail events 16..63 vanish.
  - prior art: Ableton and Bitwig both record automation PER TRACK into whatever clip is currently playing on that track, with a per-track punch that cleanly ends when the clip changes. A single global recorder pointer is not how either does it.
  - fix: Make record state per-lane: a QuantizedRecordWindow + pass + commit-target per lane, driven by that lane's live active clip each tick, with an explicit punch-out when ln.active changes mid-pass (commit the partial into the OLD clip, punch-in the new). Keep the global recorderId as the single-WRITER machine gate, but fan the pass/target out per lane.
- **[major]** The signature '1/4-speed same-length = clean 4-bar variation' has no phase-alignment guarantee: note and automation playheads are independent per-lane accumulators anchored to their own launch instants, with no re-anchoring — the same free-running mechanism the code celebrates as 'generative coprime drift' breaks the commensurate case.
  - fail: Note lane: len 16, div 1 → loop 16·stepDur. Automation lane: len 16, div 1/4 → loop 64·stepDur = 4 note loops. For 'variation over a 4-bar sequence' the automation's step-0 must coincide with a note step-0 every 4th note loop. But each lane resets stepIndex=0; nextStepTime=currentTime+0.01 at ITS launch instant, and quantized launches snap to the currently-playing clip's boundary — so if automation is enabled/launched after the notes have looped 2.5×, the slow sweep is permanently 2.5 bars out of phase with the bar grid and 'variation' smears across bar lines. Even launched together, the two lanes advance via repeated FP += (note: stepDur ×64; auto: 4·stepDur ×16) which are algebraically equal but diverge by ULPs, slipping a scheduler tick over a long set. Nothing in tick() realigns the automation wrap to a note wrap — recordTick and laneFracStep key off the automation clip's OWN playhead decreasing, and the doc explicitly leaves coprime lengths drifting.
  - prior art: Bitwig 'polymetric automation' is deterministic because both loops derive from the SAME transport phase and realign at their LCM (5-beat vs 4-beat realign every 20 beats); Ableton anchors the unlinked envelope to the clip's launch and warns users to match loop endpoints. Our independent per-launch phase origins give neither guarantee.
  - fix: Derive both the note and automation playhead phase from a COMMON transport-relative origin (the shared RST/transport-start anchor the card already claims for rates), not each lane's launch instant, so a commensurate automation loop lands on note-loop boundaries deterministically. Compute wrap times from origin+n·laneDur (not repeated +=) to kill FP drift, and expose whether a given (len,div) pair is commensurate vs drifting so the user knows which regime they're in.
- **[minor]** Migration from the current model (one automation clip per player + data.automation.clip pointer, schema v2) to embedded-per-note-clip is ambiguous/lossy, and the arbitrary-length + 4000-event cap silently tail-truncates while multiplying durable size across up to 512 cells.
  - fail: Current saves hold ONE automation clip (a real cell) whose tracks target arbitrary (nodeId,paramId) with no association to any particular note clip. Moving to 'each note clip implicitly owns its automation' has no clean 1:1 target: which of a lane's note clips inherits the single old clip's tracks? Migration is a heuristic guess or a data drop, and needs a schema v3 bump on top of the just-shipped v2 (migrateClipPlayerData). Separately, MAX_AUTOMATION_EVENTS=4000/track truncates via .slice(0,4000) AFTER sort — a long/slow 'arbitrary length' pass at ~30 pts/s hits the cap in ~133s and silently loses its TAIL with no user signal; and a per-clip model lets each of up to 512 cells carry 16×4000 events, so a whole-node Y snapshot/load and each per-wrap whole-clip reassign of a near-cap clip becomes a large recurring update.
  - prior art: Elektron surfaces a hard, visible p-lock budget (80 params/pattern) rather than silently dropping; Bitwig 6 shipped an explicit automatic project converter when it re-homed automation between storage models rather than a lossy in-place remap.
  - fix: Treat the model change as a real schema v3 with an explicit (documented, possibly lossy) migration path, or a clean break for the unreleased branch. Surface the event cap in the UI (count/max, warn near limit) instead of silent tail-drop, and cap total durable automation per player, not just per track, so the node blob and per-wrap reassign stay bounded.

### param-jump-discontinuity — verdict
The owner's per-clip direction is the right architecture (it matches Bitwig 6 / Ableton unlinked-envelope prior art), but on this dimension it makes the hazard WORSE, not better, and the current implementation has zero of the mitigations the prior art relies on. Two structural facts drive everything: (1) `scheduleParam` (engine.ts:603) never calls `cancelScheduledValues`/`cancelAndHoldAtTime` — it only piles setValueAtTime/linearRamp onto the target AudioParam — and there is NO restore path anywhere when automation stops (a stopped lane just `continue`s at clipplayer.ts:966). So every discontinuity is either a hard `setValueAtTime` step or an indefinite freeze. (2) Moving automation onto each note clip means a single mapped control is driven by a DIFFERENT envelope in every clip of its lane, so a clip switch — the most frequent user action on a clip launcher — becomes a per-control jump event, multiplying the owner's hazard by (clips launched × mapped controls). The direction can hold, but ONLY if you ship the layered default policy below BEFORE the per-clip rewrite: cancelAndHold + hold-last-value on stop (never snap to default/zero — that's the Bitwig complaint), an always-on few-ms glide across every unavoidable seam, override-release on physical touch-END rather than loop-wrap, author-a-value-into-every-clip at map-time, and an absolute-vs-offset mapping switch. Without these, the per-clip model will jump constantly and audibly. The must-fix items are the first five findings; #2 and #7 are live bugs in the CURRENT branch, not just future risks.
- **[blocker]** The per-clip model turns clip-switch into a per-control jump event with no takeover, no glide, and no restore — every launch either hard-steps a mapped param to the new clip's step-0 value or freezes it at the OLD clip's last value forever.
  - fail: Lane 1 has clip A (maps cutoff, envelope ends at 0.2) and clip B. Launch A → cutoff plays to 0.2 via scheduled ramps. Launch B. Case 1: B has a cutoff track starting at 0.9 — B's first playbackStep schedules setValueAtTime(0.9, emitAt): an instant hard jump 0.2→0.9 (a click). Case 2: B has NO cutoff track — the `activeClip.kind==='automation'` branch stops running, nothing is cancelled, and cutoff is left FROZEN at 0.2 (the previous clip's value) indefinitely, plus a 200ms ghost tail of already-scheduled ramps keeps moving it after the switch. The user expected B to sound like B, but a control is stuck at a value bled in from A. Because each of N mapped controls hits this on every launch, the owner's 'params jump wildly when clips change' hazard is not an edge case — it is the common path.
  - prior art: Bitwig Launcher snaps an un-automated param to its DEFAULT/zero on clip end (the exact 'wild jump' users beg to disable via an unshipped 'floating' mode). Ableton is more forgiving: a clip envelope MOVES WITH the clip so a defined value always exists, and an un-automated param HOLDS its last value rather than snapping. Neither hard-steps without the option of a glide.
  - fix: Adopt HOLD-LAST-VALUE as the default automation-off behavior (beats both DAWs — never snap to default/zero), but implement it deliberately: on any automation-stop for a param, call cancelAndHoldAtTime(now) so the ghost tail dies and the value is pinned. On a clip switch INTO a clip that automates the param, do NOT setValueAtTime — linearRampToValueAtTime over a per-lane glide (5–30 ms) from the held value to the new step-0 value. Offer per-mapping ABSOLUTE vs bipolar-OFFSET (Ableton automation-vs-modulation / Bitwig modulators): OFFSET mode keeps the manual base put and only a small offset changes at a switch, which is the single strongest STRUCTURAL fix for cross-clip jumps.
- **[blocker]** Touch-override is auto-cleared at the LOOP WRAP (suspended.clear() in recordTick/disarm), and notifyAutomationTouch fires only on pointerdown — so a knob gesture that spans a wrap loses its suspension mid-drag and the param is yanked to the recorded envelope while the user is still physically holding it, with live drag then fighting scheduled playback.
  - fail: Automation clip is short (encouraged by the owner's arbitrary/short-length feature). Arm, grab cutoff (pointerdown → suspended.add), and sweep it slowly across two loops WITHOUT lifting. First wrap: recordTick returns 'wrap' → commitPass + beginPass + suspended.clear(). Your cutoff key is now un-suspended and no pointermove re-fires notifyTouch (it only fires on pointerdown/wheel). Next tick: playbackStep is no longer suppressed, so it schedules the just-recorded envelope onto cutoff — the knob jumps out from under your stationary/moving hand, and for the rest of the drag your setParam and the scheduled envelope BOTH write the same AudioParam (audible fight). Meanwhile recordTick's `if (!suspended.has(key)) continue` means your held value is no longer being sampled, so the second loop records nothing. This is a live bug on the current branch, not just a future risk.
  - prior art: Ableton TOUCH stops recording/override on physical mouse-release ('recording stops immediately when you let go of the mouse button'); Bitwig TOUCH stops 'once you stop interacting with a parameter.' Neither ties override release to a musical loop boundary — precisely so a gesture that crosses a loop point is never interrupted. The current 'release at wrap' model is a novel divergence that guarantees a mid-gesture jump.
  - fix: Release the override on the actual touch-END (pointerup for screen, a short CC-idle timeout for MIDI/Electra), NOT the loop wrap. Fire notifyAutomationTouch on pointerdown AND keep a 'held' flag until pointerup so a wrap can't clear an active grab. On release, apply a short return-to-baseline glide (Deluge's ~1s smooth handback is the reference) rather than a hard revert. Keep re-sync-to-written-automation as an explicit gesture (re-launch the clip / the override dot), never automatic.
- **[major]** No cancelScheduledValues/cancelAndHoldAtTime anywhere in the automation path means the 200ms LOOKAHEAD_S window of pre-scheduled ramps keeps driving a param after you grab it or after the clip stops — the param ignores your grab / keeps drifting for up to 200ms, then freezes.
  - fail: During automation playback, grab a mapped knob. notifyTouch suspends FUTURE playbackStep calls, but the previous tick already scheduled setValueAtTime/linearRamp events up to 200ms ahead. Those queued events are never cancelled, so your manual setParam(now) is immediately overridden by the next queued automation event ~1 tick later, and the knob visibly 'snaps back' toward the envelope for up to 200ms before your value sticks. Same mechanism on clip-stop: the lane goes ln.active===null and just `continue`s (clipplayer.ts:966), so the param keeps moving along its last scheduled ramp for the lookahead tail, then freezes wherever that tail ended — a small unpredictable drift on every stop.
  - prior art: This is the standard reason Web Audio automation code calls cancelAndHoldAtTime(now) at the moment control changes hands; every DAW's touch/latch punch-in/out uses proper Begin/End gestures (Bitwig's plugin note explicitly calls out needing clean punch in/out) so the engine stops feeding the old source the instant the hand takes over.
  - fix: On suspend (touch) AND on automation-stop, call param.cancelAndHoldAtTime(ctx.currentTime) for the target so the ghost tail is truncated at its current value, THEN either let the manual value take over (touch) or hold-last / ramp-to-base (stop). This one call removes the 'knob fights back' feel and makes stop deterministic.
- **[major]** Loop-wrap is a hard setValueAtTime step whenever the envelope's start value != end value, and the owner's signature different-length/different-clock workflow GUARANTEES the automation loop wraps at a point misaligned with the notes, so a click at the wrap is the norm rather than the exception.
  - fail: stepRampPoints emits the step-0 anchor as {value:v0, ramp:false} → setValueAtTime(v0, emitAt). The previous loop's last step ramped to automationLinearAt(events, len) (the end value). If start(0.1) != end(0.8), the wrap does a hard 0.8→0.1 step every loop = a zipper click. With the owner's '1/4-speed, coprime, or arbitrary length' automation lane, endpoints essentially never line up, so this fires on every automation loop, audibly, for continuous params like cutoff/volume.
  - prior art: Elektron offers explicit parameter-lock SLIDE to glide one step's value to the next; Deluge Automation View has an interpolation on/off toggle and always-interpolates live gold-knob records precisely to avoid stepped jumps; standard DSP practice de-zippers any param write with a 1–25 ms one-pole. Ableton users are told to match envelope loop endpoints for clean loops.
  - fix: Make the last-step→step-0 transition a short linearRamp (a per-lane 'glide', 5–30 ms) instead of setValueAtTime, so the wrap becomes an inaudible ramp. Add a per-segment STEP-vs-SLIDE toggle (Elektron slide / Deluge interpolation) including at the wrap seam, and surface a 'match endpoints' affordance. Keep de-zipper always-on as the cheap baseline that covers wrap, clip-switch, and handback jumps at once.
- **[major]** Multiplayer-specific: automation playback writes only the transient AudioParam + local knobValues cache, never node.params/Y.Doc, so on clip-stop/switch each peer freezes the target param at whatever its OWN scheduling phase last produced — peers diverge with no reconciliation. No single-user DAW has an analog to copy.
  - fail: Two peers both play the automation clip (playback runs on every client). Peer A's tick and Peer B's tick sample the envelope at slightly different phases, so they schedule slightly different last values. A peer launches an empty slot / stops the lane. Now cutoff is frozen at 0.42 on peer A and 0.44 on peer B, permanently, because nothing writes an authoritative resting value to the shared store. Over a session of stops/switches these divergences accumulate, so collaborators literally hear different mixes and a reload snaps everyone to yet a third value (node.params, the last manual value).
  - prior art: Bitwig/Ableton/Deluge are single-user, so their 'hold last value' has one deterministic writer. patchtogether's memory rule 'CV modulation must not write the live Y.Doc' correctly keeps playback transient — but that means the automation-OFF resting value must be defined by a deterministic rule, not by whichever peer's audio phase happened to fire last.
  - fix: Define the automation-off resting value deterministically: on stop, snap-hold to the exact envelope value at the stop step (a pure function of clip data + playhead, identical on every peer), applied via cancelAndHoldAtTime, rather than 'whatever was last scheduled.' If you want the rest value to persist visibly, write it once through the single-writer seam (like commit) so all peers converge; otherwise document that automation-off is a pure recompute so peers agree by construction.
- **[major]** Discrete/stepped params get no authored value at map-time, so under the per-clip model a discrete control frozen at one clip's hold value stays there forever on any clip that doesn't automate it — Ableton's 'unspecified discrete param' gotcha, made permanent by the no-restore design.
  - fail: Map a 4-position waveform selector to lane 1. Clip A automates it and leaves it on position 3. Launch clip B, which has notes but no track for the selector. interp='hold' means playbackStep never runs for it (no track) and nothing restores it, so the oscillator is stuck on waveform 3 for clip B even though you never automated it there — and because it's discrete there's no glide to hide it; it's just wrong until you manually touch it.
  - prior art: Ableton documents exactly this: unspecified discrete params snap to 0/127 between clips, and the community-standard fix is to explicitly write a value into EVERY clip's envelope. The owner's 'map to exactly one lane' rule is the perfect hook to automate that fix.
  - fix: At map-time (right-click → map to lane, or auto-capture), stamp the control's CURRENT value as a single breakpoint into EVERY existing clip in that lane (and into new clips on create), so there is never an unspecified hole. This makes clip-switch deterministic for discrete AND continuous params and lets Finding #1's glide always have a defined target to ramp to.
- **[major]** In the per-clip model the recorder's commit races the queued launch at the loop wrap: recordTick commits AT the wrap while applyLaneQueued also swaps the active clip AT the wrap, so a captured pass can be written into the wrong (newly-launched) clip, producing an envelope that clip never recorded → jump next loop + silent data corruption.
  - fail: Arm, record moves into clip A while a launch of clip B is queued quantized-to-loop. At the wrap, the lane while-loop's applyLaneQueued swaps ln.active A→B, and recordTick's 'wrap' transition fires commitPass. If automationRecordTarget is resolved as 'the clip currently playing on the armed lane' (the per-clip design), it now points at B, so A's captured pass merges into B. B suddenly owns automation the user performed against A; on B's next loop those events play back and the param jumps to a curve that doesn't belong to the clip. The current single-pointer impl dodges this only because the target is a FIXED (slot,lane); the per-clip generalization reintroduces it.
  - prior art: Bitwig/Ableton bind an overdub pass to the clip that was playing when the pass began and punch out cleanly at that clip's boundary; a queued launch swaps clips at the boundary but the finished pass commits to the clip it was recorded against, never the incoming one.
  - fix: Latch the record target to the clip instance that was playing at pass-START, and have commitPass write to THAT latched (slot,lane), not to 'currently playing.' Order the tick so the pass commits BEFORE applyLaneQueued swaps the clip, or defer the swap until after commit. Add a unit test: queued launch landing exactly on the wrap must commit to the outgoing clip.
- **[minor]** CV cable + automation both target inputs[paramId].param and therefore SUM, while record reads the store (node.params) not the summed live value — so what you hear during playback differs from what gets recorded, and on touch the manual setParam fights both the scheduled tail and the live CV.
  - fail: cutoff has an LFO CV cable AND is mapped to a lane. scheduleParam writes the intrinsic AudioParam; the CV cable sums on top, so audible cutoff = envelope + LFO. But readNorm captures node.params (envelope only), so re-recording a pass drops the CV contribution — the recorded curve plays back lower/different than what you heard while performing it, a subtle 'it didn't record what I did' jump. On grabbing the knob, manual setParam(now) lands on the same intrinsic the 200ms ramp tail and the CV are all writing → a brief three-way fight.
  - prior art: Ableton/Bitwig separate ABSOLUTE automation (defines the value) from MODULATION/modulators (offset a base), so CV-as-offset and automation-as-absolute never ambiguously sum; the user chooses per mapping.
  - fix: Make the mapping's ABSOLUTE-vs-OFFSET choice (Finding #1) also govern CV interaction: absolute automation should own the intrinsic and treat CV as an explicit offset, or route automation and CV to distinct summing stages with defined semantics. At minimum, cancelAndHold on touch (Finding #3) removes the three-way fight, and document that automation captures the store value, not the CV-summed value.

### record-length-ux — verdict
The decoupled-length direction itself is SOUND and prior-art-backed — Ableton unlinked clip envelopes and Bitwig 6 "Custom Loop"/polymetric automation both ship exactly the owner's "1/4-speed-same-length → variation over 4 bars" case, so ship the unlink. BUT the current recording machinery (branch feat/clip-automation-lane) is silently built for the case where automation ≈ the loop you are watching, and it BREAKS in three concrete, code-verified ways the moment the automation loop is longer than the note loop: (1) a full-loop overdub replaces a touched track's ENTIRE loop window from a single touch (clip-automation-controller.ts commitPass → mergeAutomationOverdub window [0,len)), so you cannot punch-fix one region of a long take; (2) there is no whole-pass position cue — clip-automation-render.ts publishes only a 4-beat YYRR pre-roll, and it is wrap-relative so on the coprime lengths the UI advertises it pulses OFF the song beat; (3) release never punches out (automation-touch.ts has no release path; suspended clears only at the far-off automation wrap), so a mapped param freezes at its release value for the rest of a multi-bar loop, then jumps — precisely the owner's "params jump wildly" hazard, length-amplified. MUST CHANGE before this direction is usable: make touch-overdub punch OUT on release and merge only the held sub-window (Ableton/Bitwig TOUCH semantics); add a whole-pass progress indication on the SONG beat grid, not a 4-beat wrap-relative flash; express the automation length as an explicit musical MULTIPLE of the note clip with a Linked/Custom-Loop lock rather than two raw numbers; add a per-step grid edit escape hatch for long takes. Keep per-clip automation PRIMARY (it maps to pads); treat arranger-automation as a strictly later screen-only layer and cap sanctioned per-clip multiples so a "long automation" clip does not silently become a de-facto arrangement no LED countdown can make legible.
- **[blocker]** A full-loop overdub replaces a TOUCHED track's ENTIRE loop window, not just the region you held — so on automation longer than the note clip, one brief touch anywhere rewrites the whole multi-bar take. In clip-automation-controller.ts, beginPass seeds each track's RecordGate with sample(0, startVal) where startVal = the modulation-free STORE value (the manual base, unrelated to the envelope's step-0 value during playback). The capture loop samples only while suspended, and commitPass on a wrap passes windowEnd=len, so mergeAutomationOverdub(existing, incoming, 0, len) discards ALL existing events in [0,len) and replaces them with incoming = [seed@0 .. touch-samples]. Result: the pre-touch region [0, firstTouch) becomes a straight seed→touch ramp (original shape wiped) and the post-release region becomes a flat hold to the wrap.
  - fail: Automation lane at 1/4 speed = a 4-bar loop over a 1-bar note clip, holding a nice hand-drawn filter curve. You want to nudge just the bar-3 peak, so you grab the filter knob for one beat in bar 3 and let go. On the next wrap, commitPass replaces the whole [0,len) window: bars 1–2 collapse into a straight line from the (stale manual-base) seed value up to where you grabbed, and bar 4 flattens to a hold at your release value. Your one-beat correction destroyed the entire 4-bar envelope.
  - prior art: Ableton TOUCH mode: 'once you stop interacting with a parameter, recording is halted and any preexisting values are preserved.' Bitwig TOUCH is identical. Both record ONLY the held sub-window and leave the rest of the (longer) envelope intact — the exact opposite of this whole-loop replacement.
  - fix: Bound the overdub merge window to the actually-held span [firstTouchStep, lastTouchStep), not [0,len). Punch the record window in on touch-DOWN and out on touch-UP (see the release finding), and never seed the gate from a stale store base — anchor the pre/post boundaries to the existing envelope's values so untouched regions of a long loop survive a spot fix.
- **[blocker]** There is no position cue across a long automation pass — the performer records automation spanning N note loops but the only on-surface signal (clip-automation-render.ts) is a 4-beat YYRR pre-roll before the wrap. Worse, beatsToLoopEnd is computed WRAP-relative (((len-frac)*laneDur)/secPerBeat with automationCountdownOn keyed to that phase), so on the coprime/non-integer-beat lengths the card explicitly advertises as a feature (7, 13, …), the countdown pulses land off the transport beat grid and actively mislead.
  - fail: You set the signature 1/4-speed 4-bar automation over a 1-bar note loop and want the sweep to peak at bar 3. The note pad relaunches identically 4×, giving zero indication of where you are in the 4-bar automation pass, and the YYRR only appears in the last 4 beats (bar 4). You cannot tell bar 2 from bar 3, so you can't place the peak — you have to count bars in your head. Set the length to 13 steps for generative drift and the 'on-beat' YYRR pulses now flash a half-beat off the music you hear, so even the pre-roll is unusable as timing.
  - prior art: Ableton and Bitwig render a moving envelope playhead sweeping across the whole (longer) automation region — you always see your position in the loop. The Deluge Automation View shows the entire lane as a scrubable grid. All DAW count-ins/metronomes pulse on the SONG beat, never wrap-relative.
  - fix: Publish a whole-pass progress indication (a position-in-loop 0..1 that the card and grid can render as a sweeping bar / lit column across the automation length), not just a terminal flash. Quantize any beat-flash to the SONG beat grid, not the automation wrap. On the Launchpad, use the RGB column height/brightness to show pass position in the lane color (Deluge overview idiom) so a long take is legible without a screen.
- **[major]** Releasing a mapped control does NOT punch it out. automation-touch.ts exposes only notifyAutomationTouch (a set-add via controller.notifyTouch); there is no release notification. suspended clears only at the automation loop wrap (recordTick) or on disarm/override-dot. So during playback OR recording of a LONG automation loop, a touch-and-release leaves the param frozen at the release value (playbackStep early-returns for suspended tracks) for the entire remainder of the multi-bar loop, then jumps to the envelope at the far-off wrap.
  - fail: During a 4-bar automation loop you tweak a mapped resonance knob in bar 1 and let go. The param stays stuck at your release value through bars 2, 3, 4 (automation playback suspended the whole time), then snaps to the recorded envelope value at the bar-4 wrap — an audible multi-bar freeze followed by a jump. This is exactly the owner's 'params jump wildly when clips get changed' hazard, made worse by length: the longer the loop, the longer the freeze and the bigger the accumulated divergence before the jump.
  - prior art: Deluge gold-knob record auto-stops writing ~1 second after you stop touching and applies 'a smooth transition back to the original value.' Ableton mouse=touch 'recording stops immediately when you let go.' Both punch out on release; neither holds till the loop wraps.
  - fix: Add a release seam (pointer-up / CC-idle timeout / Electra release) that punches the param out of suspended on release, then glide (few-ms to ~1s) back to the envelope value rather than holding to the wrap. This also fixes half of the blocker overdub-clobber above (a real punch-out bounds the merge window).
- **[major]** Setting the 'multiple' is two independent raw numbers — LENGTH in steps and DIV rate — with no 'N× the note clip' lock and no musical-unit expression. The card advertises 'any count is allowed (7,13,…), NOT snapped to a bar,' and DIV is a separate 1/8..4x select. The user must derive that length-in-steps × div-multiplier = wall-clock duration = number of note loops covered, and two different (length,div) pairs give the same duration at different breakpoint resolutions with no guidance. A typo'd length silently drifts against the notes forever with no warning. (Also: in the CURRENT separate-clip impl the automation clip has no reference to a note clip at all, so the owner's '1/4 speed of the underlying clip at the same length' cannot even be expressed — it's a free-floating clip.)
  - fail: Performer wants 'automation plays once over 4 note loops' for a 16-step note clip. Path A: length 16, div 1/4 → correct duration but only 16 breakpoints smeared over 4 bars (coarse). Path B: length 64, div 1 → same duration, 64 breakpoints (fine) — but they had to know to multiply 16×4. Nothing tells them these are equivalent-duration/different-resolution, and typing 15 instead of 16 gives a permanent drift they didn't ask for.
  - prior art: Bitwig Custom Loop sets Loop Start + Loop Length in bars/beats and names the case 'polymetric automation' (the manual example is literally '1 bar + 1 beat'). Ableton drags the envelope loop braces in bars:beats against the visible clip. Both express automation length in the SAME musical unit as the clip, so 'once over 4 bars' is directly legible.
  - fix: Offer a musical-ratio picker relative to the note clip (½×, 1×, 2×, 4× length) plus an explicit Linked/Custom-Loop toggle (Ableton 'Linked' / Bitwig 'Custom Loop'). Keep raw length/div as an advanced unlinked override, and surface a drift indicator when the ratio is non-integer so 'generative drift' is opt-in, not a typo.
- **[major]** Punch-in and correction latency both scale with the (long) automation loop, with no escape hatch. QuantizedRecordWindow punches in at the automation clip's OWN next wrap — an INVISIBLE moment for a long/coprime clip that coincides with no note bar the performer hears — so you arm and wait up to a full multi-bar loop before anything records, with no 'start now' override. And because commit happens once per wrap, a flubbed move in bar 1 of a 4-bar take can't be corrected until the pass wraps 4 bars later; meanwhile the flubbed tail plays. The card has ONLY live overdub — no hold-pad-to-set-a-step p-lock — so there is no way to fix a single point of a long take without re-performing the whole pass.
  - fail: You arm on a 4-bar automation loop just after its (unseen) wrap. Nothing records for almost 4 bars; you start moving the knob 'to be ready' but it isn't being captured. When punch-in finally fires you're mid-gesture at an arbitrary position. You misjudge the bar-2 value; to fix it you must wait the full loop and re-perform the entire 4 bars because there's no per-step edit.
  - prior art: Push records into the clip you're watching launch (visible punch). Ableton lets you immediately mouse-draw a fix to any point of the envelope; Deluge/Elektron let you hold a step pad and set/p-lock just that step. All give a per-point edit path that doesn't require re-performing the whole loop.
  - fix: Add a 'punch in now' option (start the pass at the next SONG beat, not the invisible automation wrap) and adopt the Deluge/Elektron grid-edit idiom on the card: hold pad(s) → set/nudge the value for just that step's time slice, so a single point of a long take is fixable without a full re-record.
- **[major]** The arranger-automation alternative and per-clip automation collide on the same card and pull in opposite hardware directions. The card already ships TWO record buttons with overlapping mental scope — red ● arranger record (records clip LAUNCHES) and teal ◉ AUTO (records knob moves) — and arranger mode currently captures launches but NOT parameter automation. Meanwhile a 'long' per-clip automation loop is conceptually a mini-arrangement stuffed inside one clip, so letting per-clip length grow arbitrarily duplicates the arranger's job while remaining illegible on an 8x8 grid.
  - fail: A user in SONG/arranger mode expects the red record button to also capture their knob automation across the song (that's what arranger automation means in Bitwig/Deluge), but it only logs launches; their knob moves go nowhere. Separately, another user sets a 32-bar per-clip automation loop to 'automate across the whole song,' recreating an arrangement inside a clip that no YYRR countdown or 8-pad column can make navigable.
  - prior art: Bitwig/Deluge split the two cleanly: per-clip (launcher) automation LOOPS on every launch and is pad-native; song-long evolving automation lives in the ARRANGER on a timeline. Ableton lets you print/consolidate session clip envelopes INTO arrangement automation — one direction, explicit.
  - fix: Keep per-clip automation the PRIMARY, launchpad-native model (it maps to launching a pad). Cap sanctioned per-clip multiples to small musical ratios (≤~4×) behind the explicit lock so a clip can't silently become a de-facto arrangement. Treat arranger-automation as a strictly LATER screen-only layer (a timeline editor, since the Launchpad can't scrub song time) that clip automation OVERRIDES while a clip plays, with a 'flatten/consolidate to arranger' path for song-long evolution — do NOT block per-clip on it, and unify the two record buttons' semantics so 'record' means the same thing in both modes.

### completeness-critic — verdict
The per-clip direction is real prior art for LENGTH decoupling (Ableton unlinked envelopes / Bitwig Free-Running + Custom-Loop) and worth building — but as specified it is NOT buildable yet, for three completeness reasons the digest glosses over. (1) The owner's two sentences — "automation clip 1:1 tied to a note clip" and "each note LANE has an automation lane with its own clock/length" — are contradictory about who OWNS length+div (the clip or the lane); that ambiguity has to be resolved before any data model is chosen. (2) Moving tracks onto the note clip while keeping the current whole-clip-plain-reassign commit REINTRODUCES a multiplayer clobber of note data that the current separate-clip model structurally avoids — a regression, not a port. (3) The current impl (and the design) ship a record-and-delete-whole-track path with NO way to VIEW or EDIT the recorded curve, which is exactly the launchpad-native surface (Deluge Automation View) the research says is the core of the feature. Also under-specified: interaction with CV cables already patched to the same param, recorder-crash/lease, undo, and snapshot/audio clips. Resolve ownership first; store tracks in a nested per-target Y structure (not a whole-clip blob); build the view/edit surface with the record path, not after.
- **[blocker]** "Per-clip automation (1:1 tied to a note clip)" and "per-lane automation lane with its own clock-multiple + length" are contradictory about who OWNS length/div — clip or lane — and the answer changes the whole data model. The current code makes it a CLIP property (AutomationClipRecord.lengthSteps + .div, latched per clip); the owner's prose makes it a LANE property ("set the automation LANE to 1/4 speed").
  - fail: Lane 1 holds clip A (natural 16 steps) and clip B (natural 32 steps). User sets "the automation lane" to 1/4 speed / same length and records the signature 4-bar variation into A. They launch B in the same lane. If length/div is a LANE property, B's automation now runs at A's ratio and jumps/misaligns to B's musical loop; if it's a CLIP property, the "set the lane to 1/4" gesture silently didn't apply to B at all. Either way the user's mental model breaks the first time two differently-sized clips share a lane — which is the normal case in a clip launcher.
  - prior art: Ableton and Bitwig sidestep this because the automation envelope/clip is unambiguously PER-CLIP and carries its OWN Linked/Custom-Loop length; there is no separate "lane" length knob competing with it. Bitwig's polymetric example is a per-clip Custom Loop, not a lane setting. Pick the per-clip owner (as the code already does) and DROP the "per-lane length/clock" framing, or make the lane setting an explicit default that stamps into each new clip.
  - fix: Force a decision before building: make length+div a property of the (implicit) per-clip automation object (matches Ableton/Bitwig and the existing AutomationClipRecord), and re-cast "automation lane" as a per-clip default + a VIEW, not an independent length owner. Write down the answer for the differently-sized-clips-in-one-lane case as an acceptance test.
- **[blocker]** Putting tracks ONTO the note clip while keeping the commit as a whole-clip PLAIN reassign (clipplayer.ts commit → d.clips[key] = plainAutomationClip({...rec, tracks})) reintroduces a last-write-wins clobber between note edits and automation commits on the SAME Y map key. The current separate-'automation'-kind clip avoids this precisely because notes and automation live at different clipIndex keys.
  - fail: Two users on one rackspace. User A opens the piano roll of clip (lane1,slot0) and drags a note — the card writes it via rebuild-and-assign-whole (ClipplayerCard.svelte line ~186: "SyncedStore Y.Arrays reject index assignment — rebuild + assign whole"). User B has global ARM on and is overdubbing automation into the same playing clip; every loop wrap the recorder does d.clips['0'] = wholeClipObject. In the per-clip model that object now carries BOTH steps and tracks, so B's per-wrap reassign replaces the entire Y.Map at key '0' — A's just-added note is on the now-detached old subtree and is discarded on merge. Note data is silently lost during automation recording. This does not happen today (automation is a different key).
  - prior art: This is exactly why Bitwig 6 pulled automation OUT of note/audio clips into its OWN automation clip object rather than co-storing it — separate objects give separate merge scopes. Co-locating notes+tracks in one whole-object write throws that away.
  - fix: Do NOT store tracks as part of a whole-clip blob that gets reassigned per wrap. Keep automation as a sibling record keyed to the note clip's index (a parallel d.automation[clipIndex]) OR store tracks as a nested Y.Map keyed by target so a commit mutates only the touched track's events, never the note subtree. Never reassign the whole clip object on the recording hot path.
- **[major]** There is no way to VIEW or fine-EDIT a recorded automation curve. The card has only a track-count badge, an override dot, and LENGTH/DIV inputs (no canvas/path/polyline/draw anywhere in ClipplayerCard.svelte); the only edit primitives are overdub-re-record and removeAutomationTrack (nukes an entire param's track). No per-point move, no per-step p-lock, no range clear, no per-lane color overview of which params are automated.
  - fail: User records a filter sweep, but the last second overshoots. To fix one point they must either re-arm and overdub the whole touched region again by hand (hoping to not clobber the good part), or delete the entire track and start over. On the Launchpad Mini (no encoders) there is literally no on-hardware way to see or nudge what was captured — you record blind and can only launch or wipe.
  - prior art: The research names the Deluge Automation View (column=time, row=value, hold-pad-A + press-pad-B draws an interpolated ramp, interpolation on/off toggle) as THE most launchpad-native automation editor, and Push/Elektron as hold-step + adjust. Ableton shows the envelope in the clip and lets you drag points. Every cited tool offers view + point edit; this impl offers neither.
  - fix: Treat the Deluge-style grid view/draw editor as part of the feature, not a follow-up: at minimum a per-track curve render on the card and a hold-pad-to-scope-a-step + adjust (or two-pad ramp) grid gesture, plus a per-param range clear. Ship view+edit alongside record; blind record-only is not a completable workflow on a hardware-first surface.
- **[major]** The interaction between automation and an existing CV CABLE patched into the same AudioParam is undefined in both impl and design. readNorm deliberately reads the CV-free STORE value ("NOT engine.readParam — that double-applies live CV"), drive schedules the AudioParam via engine.scheduleParam, and notifyAutomationTouch only fires from Knob/Fader/MIDI/Electra grabs — never from patching a cable.
  - fail: User patches an LFO cable into filter cutoff, then maps cutoff to an automation lane and records while the LFO is patched. Recording captures only the static knob base (CV excluded), so what is stored is not what the user heard. On playback, automation setValueAtTime drives the intrinsic value AND the LFO cable still sums/races on the same param — the result is double-modulated and diverges from the take. Nothing suspends, warns, or reconciles the two. Reverse case: automation and a cable both fight for the param with no defined precedence.
  - prior art: This is a modular-specific hazard the DAW prior art never faces (no free patch cables into a param). Ableton/Bitwig only reconcile HAND vs automation (override/re-enable). Here a THIRD writer (a CV cable) exists and is unmodeled.
  - fix: Define the policy explicitly: either (a) automation = a bipolar OFFSET summed with the live param+CV (the digest's offset-mode, which also cures the jump problem), or (b) block/warn when mapping a param that already has a cable, and route cable-patch events through notifyAutomationTouch so patching suspends automation like a hand-grab. Decide before, not after, users hit the double-drive.
- **[major]** The single-writer recorder claim (recorderId = ydoc.clientID, gated by isAutomationRecorder) has NO lease, heartbeat, or release-on-disconnect. arm+recorderId are synced Y.Doc fields; nothing clears them when the recorder's tab closes or crashes mid-take, and disarm-with-commit only runs on the recorder client.
  - fail: User arms, launches a clip, is 3 loops into a continuous-overdub take, and closes the tab (or crashes). arm stays true and recorderId points at a now-dead clientID. Every remaining peer sees the red pulse + 🟡🟡🔴🔴 countdown forever, but no live client satisfies recorderId===clientID, so nobody is actually capturing — a ghost 'armed but recording nothing' state. The dead client's in-flight pass is never committed (disarm runs only on the recorder), so that take is lost. Recovery requires a peer to double-press AUTO (once to force arm=false, again to re-claim). A second user arming also silently steals the role by overwriting recorderId.
  - prior art: N/A in single-user hardware tools; this is a collab-specific robustness gap. The app's own memories stress single-writer discipline and awareness — but here the writer lock has no lease against the awareness set.
  - fix: Lease the recorder role against awareness/presence: clear arm+recorderId when that clientID leaves, and treat a stale recorderId (no live client) as unarmed so the countdown stops. Surface an explicit 'who is recording' indicator so role-steal isn't silent. Consider committing partial passes to the doc incrementally so a crash doesn't lose the whole take.
- **[minor]** Per-clip automation loops IDENTICALLY on every launch, and the arranger is a separate, un-integrated system that records clip LAUNCHES, not knob moves (per the module description: "the experimental red ● arranger record (which records clip LAUNCHES, not knob moves)"). There is no path to song-long evolving automation and no flatten/promote seam between the two.
  - fail: User wants a filter that opens gradually across a 32-bar song section. Per-clip automation gives at most one loop of variation (e.g. 4 bars) then repeats forever; the arranger can sequence WHICH clip plays but cannot record or vary a knob across the arrangement. The 'automate across the song' alternative the owner floated simply doesn't exist, and nothing lets a clip's automation be consolidated onto a timeline lane later.
  - prior art: Ableton prints/consolidates session clip envelopes into arrangement automation; Bitwig/Deluge split clip vs arranger automation but let clip automation promote. The research explicitly recommends building per-clip first BUT designing the promote seam now. Neither exists here.
  - fix: Ship per-clip first (correct), but reserve the data seam: store tracks in a form that can be flattened onto an arrangement lane, and decide now whether arranger-era automation is a later layer that clip automation overrides (Ableton/Bitwig semantics). Don't let the two systems calcify as unrelated.
- **[minor]** Snapshot and audio clip kinds are defined (SnapshotClipRecord, AudioClipRecord) but their interaction with automation is unspecified, and the 'each NOTE clip has automation' framing excludes them from being automated at all. A snapshot clip RECALLS a full param scene on launch — it writes the same params automation drives.
  - fail: Lane 2 plays an automation-bearing clip driving synthX's cutoff. User launches a SNAPSHOT clip (in another lane, or a future automated snapshot) that sets synthX cutoff to a stored value on launch. The snapshot sets cutoff at launch; the automation overwrites it on the next tick (or they fight), with no defined precedence. Separately, a user who wants to automate an AUDIO clip's gain/pitch can't, because automation is bolted to note clips only.
  - prior art: Ableton clip envelopes apply to audio clips too, and there is no separate 'snapshot clip' competing for the same param. Here two param-writing clip kinds (snapshot, automation) can target one param with no arbitration.
  - fix: State the precedence between snapshot-launch writes and automation playback, and decide whether audio clips can carry automation. If snapshot clips stay, treat a snapshot as automation-at-a-point so they share one write path rather than two racing ones.
- **[minor]** Undo semantics for automation are undefined, and continuous overdub commits a whole-clip reassign EVERY loop wrap. writeData in clipplayer.ts is a bare mutate of live.data with no transaction/origin scoping, so undo granularity (if the global UndoManager even tracks these writes) is per-wrap, and each wrap re-serializes and re-syncs the entire clip (up to 16 tracks × thousands of events).
  - fail: User records a 30s take (many loop wraps), doesn't like it, and hits Ctrl-Z expecting to remove 'the take'. Instead undo (if wired) rewinds one wrap's worth of clip state, leaving a half-recorded Frankenstein — or does nothing if automation writes aren't in the undo scope, so there's no way to revert a bad take except manual delete. Meanwhile every wrap ships the whole clip to all peers, brushing the app's own 'modulation must not storm the live store' rule for large clips.
  - prior art: DAWs treat a record pass as one undoable action and diff only changed points. Per-wrap whole-clip reassign does neither.
  - fix: Scope a record take as one undo unit (transaction origin), and commit only the changed track's changed events rather than reassigning the whole clip each wrap. Confirm automation writes are in (or deliberately out of) the UndoManager scope, and measure the per-wrap sync payload for a full 16-track clip.

All four research tracks converge and settle every open decision except two minor knobs. Our design is validated as genuinely novel where it matters: arbitrary-length clip automation is a VERIFIED unmet demand (Hapax forum: 'stuck to the track length'; Deluge forum: 'the deluge isn't built that way'), and Bitwig 6 (2025) independently arrived at our exact sibling-object architecture — automation clips launched alongside the parent note clip. Decisions: (1) ANCHOR = launch-relative, unanimous across all clip-launcher prior art, zero user demand for transport-lock; (2) END = loop default + one-shot-and-hold promoted INTO v1 (it's what makes the 4-minute build-and-hold marquee story work), plus an explicit stop/switch value policy — the #1 complaint in both Ableton and Bitwig communities; (3) RECORDING = our wrap-quantized punch is a direct extension of Ableton's latch punch-out-at-loop-wrap; commit+coarsen at each note-loop wrap matches the Pro Tools/Cubase after-pass model; (4) STORAGE = keep the 30 pts/s gate, add RDP simplify at each wrap-commit, enforce the 4000 cap by progressive coarsening (never rejection/truncation) — that turns the cap from '2 min of movement' into '10+ min of surviving gesture'. Screen editor v1 = breakpoint mode + dual-timescale view (overview strip with wrap ticks + zoomed follow view); draw mode, tension editing, and phase modes are v2. Launchpad keeps arm/record/coarse-progress LEDs only (Bitwig progression-ring model). Position feedback during minutes-long takes is where ALL prior art fails — our full-screen journey playhead is the moat.

## anchorRecommendation
LAUNCH-RELATIVE, settled by unanimous evidence. Every clip-attached automation system surveyed is launch-relative: Ableton Session envelopes (linked AND unlinked) start from the envelope start marker at clip launch with no transport-phase option at all; Bitwig 6 automation clips launch as sibling clips with the parent; Deluge is launch-relative by construction; Pyramid RELATCH / Hapax RESTART are the sync-safe defaults on hardware. Transport-lock is the convention only for a DIFFERENT category (arrangement lanes, insert-FX LFOs like ShaperBox) and that school accumulated workaround demand — Cableguys had to add MIDI 1-Shot/Audio Trigger modes because timeline phase fights live use, plus PDC misalignment in Live/Logic. Zero user demand for transport-locked clip envelopes surfaced in any community searched; complaints cluster elsewhere (value persistence, launch quantize). Hybrids worth noting, both POST-v1: (1) a per-clip 'preserve journey position on relaunch' escape hatch (Ableton's Legato mode is the only prior-art escape; matters to us because a nervous pad re-tap resets a 4-minute journey — a relaunch-confirm/quantize mitigates in v1); (2) a Vital-style per-clip Sync mode (transport-phase) later — cheap if we derive playback position from clipLaunchTime now, making Sync a pure read-path toggle. Also note the hardware 'FREE' modes (Pyramid/Hapax keep-own-phase) are free-running, not transport-derived — if we ever add a second mode, keep-phase is the precedented one.

## endBehaviorRecommendation
Default LOOP the automation period; ship ONE-SHOT-AND-HOLD-FINAL-VALUE as a per-automation-track boolean IN V1 (upgrade from 'later'). Evidence: every tool that supports independent length ships both endings as an explicit toggle sitting next to the length/unlink control — Ableton's per-envelope Loop switch (on by default; off = one-shot, final breakpoint holds — the manual's own 8-bar fade-out recipe depends on hold-at-end), Bitwig Custom Loop/Free Time, Pyramid TRIG run mode, Planar2's loop switch (loop = LFO, off = envelope). The 4-minute build-and-arrive is our marquee 128x story and it is unusable without hold-at-end, so it can't wait. Deluge has NO one-shot automation at all — a genuine differentiator. CRITICAL companion decision the evidence demands: explicitly define the value policy at clip STOP and clip SWITCH — 'value stuck from the last clip' is the single most-complained-about ambiguity in both Bitwig (KVR t=431303) and Ableton (forum t=225195), and MOD WIGGLER users build 3-clip Next-Action chains to fake hold. Recommend: hold last value on stop, plus an optional per-target RESTING/DEFAULT value (Hapax 'default values' precedent) that re-asserts when a clip without automation for that target takes over. Surface the policy in UI; never leave it implicit. Vital's Loop Point (one-shot intro then loop a tail) is a cheap v2 once loop-region markers exist.

## recordingModel
Confirmed with direct precedent, plus two refinements. PUNCH: our proposal (punch at the NOTE clip's next wrap, landing at the journey's current position) extends a pattern users already know — Ableton's latch mode punches OUT exactly at the clip-loop wrap ('recording will continue until the end of the clip's loop and then will punch out automatically'); we add wrap-quantized punch-IN, defensible since journey position is only meaningful modulo the note-loop grid. Offer Live's split per input source: on-screen gestures = Touch (instant write, punch-out on release), hardware knobs = Latch (wrap-quantized punch-out). TOUCH-GATING is not just validated but explicitly demanded: the Hapax forum's requested fix is verbatim our design ('overdub only if a new cc message is received' — non-gated overdub flat-lines untouched lanes and users hate it); Elektron and Deluge gold-knob both already work this way. Do NOT parent-lock the default record path — Bitwig 6's overdub snaps to parent length and custom lengths need a separate awkward mode; ours writes at the journey's current position natively. Steal from Deluge: short smooth ramp back into the underlying journey on punch-out (~1s), and the non-destructive 'catch' affordance (manual override during playback, smooth re-follow after idle — pairs with our no-Y.Doc-write modulation rule and Ableton's gray-LED override contract). COMMIT CADENCE: per note-loop wrap, confirmed — the pass boundary is the industry's commit-and-coarsen point (Pro Tools thin-after-pass, Cubase reduction-on-pass-completion); no prior-art conflict with Yjs crash-safety commits since hardware has no equivalent. POSITION FEEDBACK for long takes is where ALL prior art fails (Hapax hides behind its 32-bar cap; Pyramid users hand-compute chain math; Live has only the editor playhead): the card shows a journey-scale playhead, 'wrap N of M / mm:ss elapsed' counter, the upcoming punch-in landing point while armed, and per-track writing-vs-overriding tint (Live's red-vs-gray LED distinction — essential because touch-gating means tracks differ mid-take). Lane auto-create on first touched param (Hapax) in v1; per-lane LOCK against re-record as a cheap follow-up.

## lengthDivModel
Per automation-track (per target, within auto[clipIndex]): (1) lengthSteps: integer step count, fully independent of the note clip — this is the primary field; (2) div: OWN clock division per track, YES — precedented and cheap (Kria gives each parameter lane its own division 1–16; Vector sub-sequencer steps run 1/16-note to 32 whole notes, achieving >100x ratios with 8 breakpoints; Pyramid CC tracks have per-track division). Own-div is how sparse long journeys stay cheap. Effective journey length = lengthSteps × div × stepDuration, launch-relative from step 0. Breakpoint positions stored normalized (0..1 of journey length) with value normalized 0..1, so length edits don't rewrite points. MAX: no surveyed tool documents a ratio cap (Ableton 'as much time as needed'; Vector >500x); honor the 128x requirement with headroom — cap the derived journey length at something operational, not ratio-based: suggest 1024 note-clip wraps or 15 minutes of wall-time at current tempo, whichever the UI can render, i.e. effectively 'no musical limit'. Hapax's 32-bar hard cap is the cautionary tale (imported data truncated, feature requests forever). DEFAULT on lane creation: length = the note clip's length, div = note clip's div, loop = on — identical behavior to today's coupled world until the user extends it (Bitwig 6's inherit-until-Free-Time pattern, minus the mode split: extending length or div just works, no toggle to discover). Length-change semantics must be explicit: preserve breakpoints beyond a shortened boundary and restore on re-lengthen (Deluge leaves this undocumented and it reads as data-loss roulette).

## storagePlan
Three-stage pipeline, all precedented: (1) LIVE GATE: keep the ~30 pts/s while-moving decimation — it's ~13x sparser than Hapax's 384 Hz raw capture and denser than what survives any DAW's thinning; cheap worst-case bound. (2) COMMIT-TIME SIMPLIFY: at each note-loop wrap commit (the industry's pass boundary — Pro Tools 'Smooth and Thin After Pass' default 'some', Cubase Reduction Level default 50%, Ableton Simplify Envelope), run an RDP-style simplify with epsilon ~0.5–1% of the 0..1 range over the just-written region. Typical 5–10x reduction on continuous wiggle; a few pts/s survive except at direction changes. This turns the existing 4000/track cap from '~2 min of movement' into '10+ min of surviving gesture detail' — the 4-min journey (7200 raw pts) fits comfortably (~700–1500 after simplify). (3) CAP ENFORCEMENT = PROGRESSIVE COARSENING, never rejection: keep 4000/track as the hard ceiling but when approaching it, raise the RDP epsilon (slope-aware: coarsen flattest/slowest segments first — Vector proves 8 breakpoints read as musical over 256 bars) until under budget. Truncation/refusal is the one prior-art behavior (Serum 480-pt, Vital 136-pt import truncation; Hapax 32-bar import chop) that reads as data loss — never do it. Tension segments (schema field from day 1) are also a storage optimization: one curved segment replaces dozens of linear points, which is exactly what Ableton's Simplify exploits. Surface usage Hapax-style (their ~1M-event pool + RAM monitor) if a track nears budget — a subtle meter, not a modal. Multiplayer caveat: run simplify only on regions the local writer just committed (single-writer per track during a take makes this safe); don't coarsen segments with a remote pending edit.

## screenEditorV1
V1 (this phase) — the Ableton-floor breakpoint editor plus the one thing nobody ships (dual-timescale): (1) FULL-JOURNEY OVERVIEW STRIP: decimated polyline, playhead dot, loop/region brace; doubles as scrub/zoom control (drag a window) — standard DAW minimap. (2) ZOOMED MAIN EDITOR that auto-follows the playhead during play/record, with NOTE-CLIP WRAP TICKS as the dominant gridline (128 ticks make a 128x ratio legible and give the punch-in quantum a visual anchor) — this directly avoids Ableton's documented wart of blanking the note overlay when unlinked. (3) Breakpoint editing: click-segment-to-add, double-click-point-to-delete (Vital's discoverable gesture), drag with grid snap + mod-key bypass, per-track CLEAR (Deluge's years-long 'how do I delete this' burden says make it first-class). Destructive ops gated behind an explicit edit mode — single-click delete is too dangerous mid-set. (4) Per-track controls: length + div fields, loop/one-shot toggle, lane list with writing(red)/overriding(gray) state. (5) Record feedback: journey playhead, wrap N of M + mm:ss counter, punch-in landing marker. DATA MODEL NOW even if unrendered: per-segment tension scalar (default 0 = linear) in the Yjs schema — every surveyed tool retrofitted curves and churned their format; linear-only RENDERING is fine for v1. LATER (v2+): draw/paint mode with grid-stepped stamping (Vital paintbrush / Bitwig spray can), tension handle editing, Loop Point partial-loop mode, per-lane LOCK, relative/modulation layer (Ableton blue envelopes / Bitwig additive — the proven answer to 'automation vs a human on the same knob' in multiplayer), per-clip Sync/keep-phase modes, linked-copy-decouple duplicate semantics.

## launchpadRole
Minimal, evidence-backed: all surveyed systems keep envelope content OFF the controller (Live/Launchpad shows only a pulsing red record pad and a clip-slot progress pie; Deluge's pad-grid playhead is explicitly useless for long journeys). The pads show: (1) clip state as today (playing/queued/stopped); (2) record-armed / actively-writing state on the clip's pad (pulsing red convention); (3) a COARSE journey-progress cue — adopt Bitwig 6's launcher progression-ring idea, the only prior art for showing position inside a multi-loop journey from the launch surface (e.g. LED brightness/color ramp or a dedicated row-LED encoding journey fraction and loop count). Nothing else: no breakpoint editing, no value display, no per-track state on pads. All visualization/editing lives on the card. This matches the converged design exactly and no evidence argued for more pad-side function.

## delugeRepeatsNotes
Reference semantics for the parked repeats feature (Deluge model): (1) Repeats belong to a GROUP/scene, not a clip — a section pad held ~0.5s enters repeat mode; select knob sets N; default INFI. (2) N is counted against the LONGEST member clip's length. (3) Semantics are 'repeat N then AUTO-ADVANCE to the section vertically below' — an implicit section sequencer, NOT play-N-then-stop; this confused users (forums.synthstrom.com/4393) who expected stop. (4) Trap: repeats are silently VOIDED unless ALL clips in the section are playing — muting one member kills auto-advance with no indication. (5) Community firmware adds per-clip launch modes: INFINITE / ONCE (plays one loop then stops) / FILL (scheduled backward from the next loop boundary so it FINISHES at the wrap; can't steal a non-fill's instrument). Design directives when we build it: offer 'N then STOP' as a first-class option alongside 'N then advance'; never let the repeat contract silently void on membership changes; and keep it fully decoupled from automation — journeys must run identically under INFI, N-repeats, ONCE, or FILL. Bitwig 6's launcher progression rings (play counts + next-action timing) are the display model for showing repeat progress.

## risks
- Value persistence at clip stop/switch is the #1 user complaint in BOTH reference ecosystems (Bitwig KVR t=431303 stuck values; MOD WIGGLER t=175742 revert-to-default; Ableton t=225195) — if we ship without an explicit, surfaced policy we inherit their top support burden.
- Launch-relative + long journeys = a pad re-tap destroys a 4-minute journey. Ableton's only mitigation is Legato mode. Launch-quantize softens it in v1; plan the 'preserve position on relaunch' escape hatch and consider a relaunch-confirm for clips with long journeys.
- Dual-timescale readability: Ableton literally BLANKS the note/waveform overlay when an envelope is unlinked (forum t=13590), losing note-vs-automation alignment exactly when timelines diverge — our editor must keep the note grid visible at 128x divergence (wrap ticks) or we repeat their wart.
- Bitwig's retrofit complexity is the warning: Free Time toggles, per-lane follow overrides, overdub that still snaps to parent length, and 'start recording before the clip' for custom lengths — all symptoms of bolting independence onto a parent-locked default. Our day-1 independent storage avoids this ONLY if we never make the record path parent-locked.
- Hard-cap rejection reads as data loss (Serum/Vital truncate on import; Hapax truncates >32-bar MIDI) — never refuse or truncate a take; coarsen progressively.
- Length-change semantics are undefined-behavior roulette in prior art (Deluge never documents truncate-vs-preserve) — define preserve-and-restore explicitly in the spec and test it.
- Single-click breakpoint delete (Ableton) is too dangerous mid-set — destructive editor ops need an explicit edit-mode gate on the card; multiplayer Yjs undo covers the rest.
- Touch-gated overdub means per-track state diverges mid-take (some tracks writing, some overriding) — without the red-vs-gray per-track indicator users cannot tell what a take is overwriting.
- Deluge's implicit launch-point computation (derived from longest playing clip) is a documented frustration and silently breaks features when clip subsets are muted — keep our launch/punch quantize rule explicit, simple, and visible.
- Duplicate/copy semantics: duplicating a note clip must carry auto[clipIndex] — Bitwig 6's linked-copy-decouples-on-first-edit rule is the model; deciding this late churns the Yjs schema.
- Automation must run identically under the future repeats feature (INFI / N / ONCE / FILL) — any coupling now recreates Deluge's 'repeat contract silently voided' class of bug.

## unsettled (evidence could not decide)
- Journey max length: evidence says 'no musical cap' (Ableton unbounded, Hapax's 32-bar cap is the anti-pattern) — is 15 min wall-time / 1024 wraps an acceptable operational ceiling for v1, or do you want it truly unbounded and let the storage coarsener be the only limit?
- Per-target RESTING/DEFAULT value (Hapax precedent — re-asserts when a clip without automation for that target takes over): v1 or follow-up? Evidence proves the stop/switch value problem is the top complaint but doesn't dictate which release ships the fix.
- On-screen gesture punch semantics: Live splits Touch (mouse = instant write, punch-out on release) vs Latch (hardware = punch-out at wrap). Do you want on-screen card gestures to write INSTANTLY (Live's mouse behavior) while hardware knobs get wrap-quantized latch, or one unified wrap-quantized rule for both? Prior art supports either; the split is what users know from Live.
- Relaunch protection for long journeys in v1: launch-relative means a pad re-tap restarts a 4-minute journey. Is the existing launch-quantize enough for v1, or do you want a per-clip relaunch-confirm / 'preserve position on relaunch' escape hatch sooner? (Ableton's only answer is Legato mode; no tool solves this well.)
- Coarsening a LIVE multiplayer doc: prior art (Pro Tools/Cubase thinning) is single-writer file-based; nothing informs how aggressive commit-time RDP interacts with a collaborator mid-edit on the same track. Accept 'skip simplify on tracks with a remote pending edit' as the v1 rule?

## Raw per-tool digests
### Ableton Live 11/12 (unlinked clip envelopes, Session View) + Bitwig Studio 5/6 (launcher clip automation, Bitwig 6 automation clips)
- ABLETON — envelope length fully independent and effectively unbounded: the Live 12 manual (ableton.com/en/manual/clip-envelopes/) documents unlinked envelopes with their own loop/region settings; its worked example is an 8-bar fade-out on a 1-bar loop ('As you play the clip, you can hear the one-bar loop fading out over eight bars'), and it states 'You can create as much time as needed in the Envelope Editor, either by dragging the loop braces beyond the view limit, or by entering values into the numeric region/loop controls.' No maximum length or ratio is documented anywhere — 128x (2s clip / 4-min envelope) is representable.
- ABLETON — the classic one-shot ramp trick is the manual's own recipe: unlink the envelope, toggle its Loop switch OFF, drag the region out to N bars, put a breakpoint at region end and drag it down — 'the sample will keep looping although the envelope is now playing as a one-shot.' Re-enabling the envelope's Loop switch makes the N-bar journey itself repeat ('you can hear the eight-bar fade-out repeating').
- ABLETON — envelope editor controls (Sonic Bloom guide + manual): Linked/Unlinked toggle at the bottom of the Envelopes tab; when unlinked you get Start/Position/Length numerics for looped clips (Start/End for unlooped) plus 'a Loop Switch for the automation right next to the Linked/Unlinked toggle', on by default for looped clips. Draw Mode draws grid steps; Draw Mode off = breakpoint/segment editing; Shift-drag = fine resolution; start/end markers and loop brace are quantized by the zoom-adaptive grid.
- ABLETON — Session clips carry BOTH envelope kinds since Live 11: red AUTOMATION envelopes (absolute values) and blue MODULATION envelopes (relative — 'you don't set the parameter to a specific value, instead you adjust within a specific range'), toggled beneath the envelope choosers; red/blue LEDs in the Control chooser mark which exist (help.ableton.com 'Working with Automation and Modulation').
- ABLETON — session automation recording (manual, 'Automation and Editing Envelopes'): Automation Arm + track Arm + Session Record; mouse = touch behavior ('recording stops immediately when you let go of the mouse button'); MIDI controller = latch ('recording will continue as long as you adjust the controller. When you let go, recording will continue until the end of the clip's loop and then will punch out automatically') — i.e. punch-out lands exactly at the clip-loop wrap. A preference (Session Automation Recording) records into ALL playing session clips regardless of arm state. Overdub is touch-gated by construction: only the parameter you move gets written; everything else in the clip is preserved.
- BITWIG pre-6 (userguide, 'The Automation Editor Panel'): launcher-clip automation decouples via the FREE RUNNING button ('the clip's automation data can now be adjusted to play back differently from the clip's notes/audio'; a Start parameter picks where automation playback begins) plus a CUSTOM LOOP button ('set different values for the automation's Loop Start and loop Length settings. When disabled, the clip's automation will loop just as the clip's musical content does'). Worked example is polymetric (5-beat automation loop over a 4-beat clip); nothing caps automation length vs clip length. Caveat: 'When any of these parameters are changed, you will need to retrigger the clip for the changes to be registered.'
- BITWIG 6 (Release-Notes-6.0.html, downloads.bitwig.com): automation became CLIP-based ('Record, edit, and create automation in meaningful, musical blocks'). A per-automation-clip FREE TIME toggle makes it 'independent in length and start time from its parent clip'; when off, Looping/Start/Length are inherited (dimmed) from the parent, and Free Time auto-enables when timing diverges. Global Follow (green) / Lock (red) button controls whether automation clips move with their parent note clips, with per-lane overrides (Always follow / Never follow / Use editor setting / Arranger lock).
- BITWIG 6 — launch coupling is explicit: 'Triggering a note/audio Launcher clip (including via Next Action) will also launch its automation clips' — automation is a SIBLING clip launched alongside the note clip, the same shape as our auto[clipIndex] sibling-object design.
- BITWIG 6 — recording: 'Automation Write now supports recording Launcher automation clips at different lengths from the original'; but 'If you enable overdub and perform automation, the resulting automation clip exactly matches the length of the parent clip' — overdub still snaps to parent length, and per polarity.me, 'To create an automation clip with a custom length, you must use standard automation writing mode and start recording before the clip.' Write modes: Latch / Touch / Write; overdub adds points per the active mode.
- BITWIG 6 — point/density machinery: per-point HOLD behavior ('staying at the current value until the next point is reached'), Spread (seeded randomization range), visible Curvature, snapping to relative beat position/clip boundaries/other points, a Spray Can tool for stepped automation at the grid interval, 'High-fidelity thinning is applied' after edits, and playback smoothing made 'time-symmetrical' with 'improved automation curve accuracy for tighter, less smoothed transitions.' No numeric breakpoint caps published.
- BITWIG — value-persistence pain in the wild: KVR t=431303 ('Clip automation persists on other clips. Why?') — 'The automation leaves the affected parameter in the position it is when the clip changes'; users resort to writing default-value automation into every other clip. MOD WIGGLER t=175742 ('Hold at automation value after clip end?') describes the opposite gap for track-level cases — 'Once a clip event ends, the automation override ends, and the track reverts to its default level' — and a 3-clip workaround (fade-in clip → Next-Action → looping 100% hold clip → fade-out clip) to fake one-shot-and-hold. The two threads together show end/stop value policy is context-dependent and confuses users in BOTH directions.
- BITWIG — arranger-side trap (KVR t=546173): drawing 'clip automation' on an unlooped arranger clip silently becomes track automation ('if we make clip automation there it's actually track automation', with a visual bug showing it as clip automation) — looping must be enabled BEFORE extending or the automation won't repeat with the clip.
- ABLETON — known UX wart with unlinked envelopes: the clip's waveform/MIDI overlay vanishes from the envelope editor once unlinked (forum.ableton.com t=13590), so you lose note-vs-automation visual alignment exactly when the two timelines diverge; historic crashes adjusting unlinked loop braces (t=106843/t=109973, long fixed). Value-persistence complaints exist too ('Reset clip envelopes on start', forum t=225195 — values only reset after pressing Stop).
- POSITION FEEDBACK — Bitwig 6 added 'progression rings on launcher clips showing play counts and when next actions trigger' (polarity.me Bitwig-6 changes post) — the only prior art found for showing where you are inside a multi-loop journey from the launcher surface itself; Ableton offers nothing beyond the envelope-editor playhead.

- LESSON: Launch-relative is confirmed as the industry norm for clip-attached automation (both tools; zero user demand found for transport-locked clip envelopes) — ship launch-relative; if transport-locked evolution is ever requested, precedent says build it as a modulator/LFO-class feature, not an anchor mode on clip automation.
- LESSON: Make loop-vs-one-shot an explicit per-automation-track toggle placed next to the length/unlink controls (Ableton's Loop switch, Bitwig's Custom Loop/Free Time) — default LOOP for looped clips, and one-shot HOLDS the final breakpoint value (Ableton's fade recipe depends on this).
- LESSON: Explicitly define and surface the value policy at clip STOP and RELAUNCH — value-stuck-after-clip-change is the top complaint in both ecosystems (KVR t=431303, MOD WIGGLER t=175742, Ableton forum t=225195); pick 'hold last value' plus a visible per-target return-to-default option, and never leave it implicit.
- LESSON: Our punch proposal has direct precedent: Ableton's latch behavior punches out exactly at the clip-loop wrap — punching at the NOTE clip's next wrap, landing at the journey's current position, extends a pattern users already know rather than inventing one.
- LESSON: Do NOT parent-lock the default record path: Bitwig 6's overdub snaps automation to the parent clip's length and custom lengths require a separate awkward workflow ('start recording before the clip') — since our storage is natively arbitrary-length, let touch-overdub write at the journey's current position and (optionally) auto-extend, avoiding Bitwig's mode split.
- LESSON: Retrigger resets the journey in both tools; Ableton's Legato launch is the only escape hatch — plan a per-clip 'preserve journey position on relaunch' option (post-v1) so a 4-min journey isn't destroyed by a nervous pad tap; a relaunch-confirm/quantize already helps.
- LESSON: Keep the note grid visible inside the automation editor even when timelines diverge 128x — Ableton literally blanks the waveform/MIDI overlay when unlinked (forum t=13590) and Bitwig 6 users complain notes are unreadable behind automation (polarity.me); our card editor needs dual-timescale rendering (note-loop ruler + journey ruler) as a first-class requirement.
- LESSON: Launchpad position cue: copy Bitwig 6's progression-ring idea — pad LED encodes journey progress/play-count and record-armed state; all breakpoint viz stays on the screen card (matches both tools keeping envelopes off the controller).
- LESSON: Storage: adopt thin-on-record + post-take 'high-fidelity thinning' (Bitwig's term) instead of a hard 4000-point rejection; add hold-type points (Bitwig 6 per-point Hold) so stepped journeys cost points only at transitions — that alone can make 4-minute journeys cheap; coarsen flattest/oldest segments when nearing budget.
- LESSON: Our sibling-object model is validated: Bitwig 6 automation clips are literally sibling clips launched with the parent note clip ('Triggering a note/audio Launcher clip will also launch its automation clips') with a follow/lock linkage — their Free Time + per-lane follow-override complexity is what retrofitting looks like; we get it for free by storing auto[clipIndex] with independent length from day one.
- LESSON: Absolute vs relative: both tools grew a relative layer (Ableton blue modulation envelopes, Bitwig additive/multiplicative automation) because absolute automation fights live knob control — our touch-gated overdub already resolves the live-control conflict Ableton-style (touch overrides, release re-records), but keep relative/modulation mode in mind as the multiplayer follow-up, since it's the proven answer to 'automation vs a human on the same knob'.

### Synthstrom Deluge (stock firmware 4.x + community firmware 1.x "Automation View" / Grid View)
- REPEATS live on SECTIONS, not individual clips, in stock firmware. A section = a color-group of clips launched together from the section pads on the far right of Song (Row) view. Hold a section pad ~0.5s until 'repeat mode' blinks on the display; default is 'INFI' (infinite); turning the select knob sets any number N. (Official manual + forums.synthstrom.com/discussion/1921 'How to use section repeat number')
- Repeat semantics: after N repeats OF THE SECTION'S LONGEST CLIP, the Deluge auto-launches the section vertically BELOW it in the grid — it is an automatic section sequencer ('rudimentary song mode'), NOT play-N-then-stop. User ehahken in forums.synthstrom.com/discussion/4393 'Repeat Mode' expected repeat=2 to 'play twice then stop' and was confused when it looped/advanced instead — Heptagen: 'the blue section repeat four times before moving on to the section that is directly below it... without you triggering the pink section at all.'
- Repeat-count edge case (same thread, user reza): 'repeat modes only are honored if ALL the clips in that color section are playing at the same time' — mute one clip of the section and auto-advance silently stops working. Users (Squirt) requested explicit next-section routing instead of implicit advance-to-row-below.
- Community firmware adds PER-CLIP launch modes via a CLIP MODE menu: INFINITE (stock default), ONCE, FILL. ONCE: 'schedules itself to start at the start of the next loop. Then it will schedule itself to stop, so it just plays once.' FILL: scheduled so it FINISHES at the start of the next loop (starts midway if longer than remaining time); the 'loop length is set by the longest playing clip, or by the total length of a section times the repeat count set for that section.' Fill clips obey one-clip-per-instrument and 'cannot steal from a non-fill.' (delugecommunity.com/features/community_features/)
- The second home of repeats is ARRANGER view: a clip instance dragged across the timeline loops for the drawn region — repeats are implicit in the drawn length, no count field. (Official manual / community guide)
- AUTOMATION LENGTH IS STRICTLY BOUND TO CLIP LENGTH — confirmed twice. Community Automation View docs: 'you cannot edit automation past the arrangement/clip length boundary'; 'Shift + turn Horizontal' changes clip length for BOTH notes and automation together. Forum (discussion/5476 'Automation View Mode'): 'Can automation run at a sequence length independent of clip/row? (Currently no, the deluge isn't built that way).' There is NO longer-than-clip automation on Deluge, stock or community, as of CF 1.x.
- Community workarounds for notes-vs-automation length divergence: (a) shorten individual NOTE ROW lengths inside a long clip — clip (and its automation) stays long while note rows loop short, giving polymetric 'long automation over short riff' (the inverse of extending automation); (b) clone the clip, delete notes from one and automation from the other, set different lengths — WORKS ONLY for MIDI/external instruments because 'it is not possible to assign two clips to the same synth preset' (one-clip-per-internal-instrument rule); (c) MIDI loop-back out-and-in. Older pre-3.x firmware allowed multiple clips per synth; its removal is itself a complaint (OdoSendaidokai, forums.synthstrom.com/discussion/2677).
- GOLD-KNOB RECORDING (official manual p.19 + delugecommunity.com/manual/device_overview/recording/): in record mode, 'any movement of a parameter knob is recorded... Recording begins when you begin to turn the knob, and ceases when the knob has been left alone for a second or so (a smooth transition back to the original value is then applied).' Existing automation is replaced 'by simply turning the parameter knob some more while still in record mode' — i.e., touch-gated overdub that loops with the clip and only overwrites where/when you touch.
- Playback override / catch: outside record mode you can 'take manual control of the parameter at any time by turning the corresponding parameter knob. Then, after leaving the knob alone for a second or so, the parameter value will smoothly transition back to follow its automated movement.'
- CLEAR gesture: Shift + press (click) down on the gold knob → display shows 'DELETE' → wipes ALL automation for that parameter in the clip; 'Parameters are reset to the current value in the Sound Editor.' External-controller variant: record+play, hold Shift, turn the external knob. Non-gold-knob parameter automation was historically effectively undeletable (forums.synthstrom.com/discussion/2501) until community Automation View added per-lane editing and an automation-only clip-clear ('clearing the clip will only clear Automations, and not the... Clip Notes').
- Community Automation View editing model: per-step pad editing 'at any zoom level' (grid default 1/16ths, zoomable to 1/128ths); the 8 pad rows bucket the 0–128 value range (16 per pad); hold-pad-A-press-pad-B enters a linear ramp between them; an Interpolation toggle (Shift + interpolation shortcut) controls smooth-vs-stepped for pad-entered ramps, and knob-recorded automation 'is always recorded with Interpolation.' No documented cap on automation nodes/density anywhere (song is serialized to XML on SD).
- CLIP LENGTH CHANGES: the automation grid simply follows the new clip length; docs never specify truncate-vs-preserve past the boundary and editing past it is impossible — undefined-behavior territory users have to discover by experiment.
- LAUNCH TIMING (community sequencer docs, seangoodvibes.github.io DelugeDocs + delugecommunity tips): armed clips launch at loop points DERIVED from playing clips — 'if none of the armed clips have multiples of the clip lengths currently playing, then the armed clips launch at the highest [longest] playing clip loop point'; muting 'occurs at the end of the longest clip length.' There is NO user-settable launch quantization in stock firmware; forums.synthstrom.com/discussion/4655 asks for a '1 bar' quantize because waiting for the longest clip's loop point is too slow/unpredictable. Clips always (re)start from their beginning at the launch point — no Ableton-style legato/phase pickup exists on Deluge.
- **anchorSemantics**: Deluge is purely LAUNCH-RELATIVE: a launched clip always starts at its step 0 (at a launch point derived from currently-playing clip loop points), and since automation lives inside the clip it is launch-relative by construction. There is no transport-locked/global-phase mode and no legato position pickup, and NO user demand for transport-locked automation phase surfaced anywhere — user complaints target the WHEN of launch (the launch point is computed from the longest playing clip with multiple-of-length rules, not a settable '1 bar' quantize; forums.synthstrom.com/discussion/4655), not the phase of what plays. This CONFIRMS our launch-relative recommendation, with a corollary: make the launch-quantize rule explicit, simple, and user-visible — Deluge's implicit derived rule is a documented frustration, and it also silently breaks section auto-advance when clip subsets are muted.
- **endBehavior**: Deluge automation has exactly one end behavior: LOOP with the clip (automation period == clip period, always). There is no one-shot-and-hold option for automation and no toggle — the only 'hold' analog is the recording punch-out ramp back to the pre-existing value. The community CLIP MODE menu (INFINITE / ONCE / FILL) shows demand for non-looping semantics but operates on the whole clip, not the automation layer. Evidence therefore supports loop-the-period as the familiar default, and one-shot-and-hold-final-value as a genuine differentiator no Deluge user can get today — worth shipping as a per-track or per-clip toggle since our journeys (unlike Deluge's) can outlive many note-loop wraps and 'arrive somewhere and stay' is the natural end of a 4-minute journey.
- **recordingUX**: Deluge's gold-knob recording is the closest hardware prior art to our touch-gated overdub and validates it: recording starts on first knob motion, punches OUT automatically ~1s after the knob goes idle, and applies 'a smooth transition back to the original value' — only the touched parameter, only where touched, everything else preserved, looping overdub-style with the clip. Two refinements to steal: (1) the release RAMP — on punch-out we should ramp back into the underlying journey's value over a short window rather than stepping; (2) the non-record 'catch' behavior (manual override during playback, then smooth re-follow after idle) is a separate, loved affordance we can offer since our params are already touch-instrumented. Two gaps we must NOT replicate: Deluge gives essentially zero position feedback during a take (128-pad grid playhead only; no timeline, no indication of where in the automation you are — fine for 2-bar loops, useless for minutes-long journeys), and its punch-in granularity is instant-on-touch with no musical quantize option; our proposed punch at the note-clip's next wrap landing at the journey's current position has no Deluge precedent to copy, but Deluge's FILL-clip scheduling ('start so that you finish at the next loop boundary') is the same boundary-aware scheduling idea. Commit cadence is a non-issue on Deluge (hardware, instant in-memory persistence + explicit song save), so our per-note-loop Yjs commit for crash safety is unconstrained by prior art.
- **limitsStorage**: No documented caps: neither the official manual nor community Automation View docs specify any maximum automation node count or density; songs serialize to XML on SD card. Effective densities: knob-recorded automation is captured continuously and 'always recorded with Interpolation'; pad-edited automation is per-step at the current zoom (down to 1/128th notes) with values bucketed into the 0–128 range (8 pads × 16); live note-record quantize defaults to 1/32nds. The practical Deluge limiter is clip length itself (automation can never exceed it), so minutes-long single-param journeys simply don't exist there — meaning our 4000-points/track cap (~2 min of continuous 30 pts/s movement) has no comparable precedent to benchmark against, and the 128x/4-minute-journey requirement pushes past it: either raise the cap, or coarsen (Deluge's own model suggests the shape: interpolated breakpoints + value bucketing tolerate aggressive decimation of idle/linear spans well; only touched regions need density).
- LESSON: Our core requirement (automation length fully independent of clip length, up to 128x) is a VERIFIED unmet demand in the Deluge world — 'the deluge isn't built that way' is the canonical forum answer and users resort to polymetric row-length hacks, clip cloning (blocked for internal synths), and MIDI loopback. We are building the thing they ask for; do not water it down to a small ratio.
- LESSON: Confirm LAUNCH-RELATIVE anchoring (step 0 at launch). No evidence anyone wants transport-locked automation phase; the real-world pain is unpredictable/implicit launch quantization — make ours an explicit, visible, simple rule (our proposed note-clip-wrap boundary qualifies) rather than Deluge's derived-from-longest-playing-clip computation.
- LESSON: End behavior: default LOOP the automation period (matches every Deluge user's mental model), and ship ONE-SHOT-AND-HOLD as an explicit per-track/per-clip toggle — Deluge has no such option and its ONCE/FILL clip modes show the appetite for non-looping semantics.
- LESSON: Recording: keep touch-gated punch-in/overdub (Deluge-proven), and copy two specifics — a short smooth ramp back into the underlying journey on release (Deluge applies one after ~1s knob-idle), and the playback-time 'manual override then smoothly re-follow' catch behavior as a separate non-destructive affordance.
- LESSON: Give every automatable target a first-class per-track CLEAR (our sibling auto[] object makes this easy) — Deluge's Shift+click-knob DELETE only covered gold-knob-learned params for years and 'how do I delete this automation' threads were a recurring support burden until Automation View fixed it.
- LESSON: Position feedback is our moat: Deluge users navigate minutes of nothing on a 128-pad grid; our full-screen card should show the journey timeline with a playhead, the punch-in landing point, and record-armed/overdub state — leave only arm/record/position CUES on the launchpad, exactly as converged.
- LESSON: Parked REPEATS feature — document the Deluge reference model: repeats belong to a GROUP/scene (N repeats counted against the longest member clip, then auto-advance to the next group; INFI default; set by hold-pad + encoder; shown as a blinking count). Two traps to design around: users expect 'N then STOP' at least as an option (Deluge only advances, which confused people), and never let the repeat contract silently void when membership changes (Deluge repeats are ignored unless ALL section clips are playing). Keep it decoupled from automation: our journeys must run identically under INFI, N-repeats, or one-shot.
- LESSON: Define automation-length-change semantics explicitly (preserve data beyond the new boundary and restore on re-lengthen, or truncate loudly) — Deluge leaves this undocumented and it reads as data-loss roulette; since our length is independent of the note clip we only face it on explicit automation-length edits.
- LESSON: Storage: no cap exists in prior art to copy; to honor the 4-minute-journey requirement either raise the 4000/track cap or add background coarsening of old takes (decimate idle/linear spans — safe because tracks are interpolated breakpoints, same as Deluge's always-interpolated recorded automation).

### Independent-length automation prior art: Squarp Hapax + Pyramid, Five12 Vector, Elektron (counterexample), Intellijel Planar2, monome Kria/Teletype, plus Ableton unlinked clip envelopes as the Session-model software anchor
- SQUARP HAPAX — automation lane length is HARD-COUPLED to track/pattern length, and this is an actively requested missing feature: 'Now it's stuck to the track length' (squarp.community/t/automation-length/16027); users want independent lane lengths specifically for polymeter modulation (filter cutoff, octave shift, decay on a different period than notes) (squarp.community/t/automation-lane-length/7594). No Squarp response committing to it. The accepted workaround is dedicating a SEPARATE track (own length, own division) sending CC to the same channel — i.e., 'automation as its own clip' is how users fake independence.
- HAPAX specs: pattern length 1 step to 32 bars (hard cap — imported MIDI longer than 32 bars is truncated); 16 tracks x 16 patterns; up to 64 automation lanes per track; automation events are stored PER PATTERN ('each pattern of a track can have different automation events') (squarp.net/hapax/manual/modeautomation/, squarp.community/t/automation-autom-question/11169).
- HAPAX automation density: 1 data point per clock tick at 192 ppqn — 'at 120BPM clock ticks are 2.6ms apart, resulting in a sampling frequency of 384Hz'; recorded automation is NOT interpolated by default 'to keep the recording faithful to the original' (drawn automation can interpolate). Project capacity ~1 million notes+events, with a RAM monitor showing a separate Automation memory space (squarp.net/hapax/manual/modeautomation/, squarp.net/hapax/manual/modesettings/, squarp.net/hapax specs).
- HAPAX pattern-change anchor is a TOGGLE: TRIG setting = RESTART ('resets the position to the beginning of the pattern after a change') vs FREE ('keeps the previous position of the player upon a pattern change') (squarp.net/hapax/manual/modepattern/). 'Default values' re-assert a parameter after a pattern change when the new pattern has no events — a third 'release to default' semantic.
- HAPAX overdub complaint = direct validation of touch-gated recording: with overdub on, lanes you STOP moving get flat-lined — 'if I moved 5 knobs and I don't keep on moving all 5 knobs the overdub setting just trace a line on that automation lane'; the requested fix is verbatim our design: 'overdub only if a new cc message is received'. Hapax's existing mitigations: per-lane LOCK ('Recording will not overwrite the lane events'), lanes auto-created on first incoming event, and switching REC to end-of-pattern punch behavior as a tedious workaround (squarp.community/t/midi-input-and-automation-overdub/8582, squarp.net/hapax/manual/modeautomation/).
- SQUARP PYRAMID — fully independent per-track lengths: 64 tracks, each from 1 step up to 384 bars with per-track time signature/division; a CC-only track IS an independent-length automation lane. Per-track RUN MODES are the anchor toggle: FREE ('track continues to play without restarting at its beginning... tracks shift against each other' — polymetric drift), RELATCH ('always restarts at its beginning. It's an easy way to sync'), TRIG ('playing once at the beginning of the sequence, and does not loop' — one-shot) (squarp.net/legacy/pyramid/manual/, Sound On Sound review).
- PYRAMID long-journey friction: sequence links cap at 64 bars, so a 256-bar track needs 'set it to TRIG, add four 64 bar links to the chain and just make sure the track stays non-muted throughout' — users call out needing 'the calculator' and fear 'less visible limitations lurking'. Long independent automation exists but the position/length bookkeeping UX fails (squarp.community/t/track-length-greater-than-sequence-length/3109).
- FIVE12 VECTOR — per-part independent lengths plus per-part rate as percent (10–120%) or odd fractions (e.g. 5/13); each part has TWO 8-step sub-sequencers with their OWN length (e.g. 5 steps against a main 8) and OWN rate from 1/16th note to 32 WHOLE NOTES per step — 'your sub-sequencer can have a long duration encompassing many sequence repeats'. That is an extreme-ratio (>100x) slow journey achieved with only 8 breakpoints; destinations include transpose, octave, rate, direction, sequence start (files.five12.com/VectorUserGuideV3.0.pdf, Sound On Sound Vector MkII review, steveturner.com.au review).
- ELEKTRON (counterexample) — p-locks are welded to steps of the pattern (max 64 steps classic boxes), so automation length = track length by construction; per-track SCALE/LENGTH mode gives polymeter and M.LEN can be INF ('loop infinitely, without ever being restarted') with CH.LEN quantizing pattern changes, but automation still cannot exceed its own track's step count. The community workaround for longer sweeps is a free-running LFO + a TRG p-lock on step 1 with a '1st' trig condition — evidence of unmet demand for >pattern-length automation (manualslib Digitakt manual p.32, elektronauts.com/t/reliably-lock-lfo-start-point/162628).
- ELEKTRON live-record UX: turning a DATA ENTRY knob in live recording mode writes p-locks only on the steps that pass WHILE you turn, quantized to steps — untouched parameters keep their existing locks. Touch-gated overdub is already the norm there and users accept it (manualslib Digitakt manual p.28).
- INTELLIJEL PLANAR2 — CV gesture recorder: 'up to 30 seconds of joystick movements and gate on/off events' (hard time cap, not breakpoint cap); loop toggle picks the end behavior — 'Depending on whether you activate looping, your CV recording is treated as a really flexible LFO or an envelope' (loop vs one-shot function); 'Punch-in/out recording is supported'; 'Start time and length can sync to an external trigger' (clock-anchored capture); Scan mode scrubs the recorded gesture at any speed/direction via CV (intellijel.com/shop/eurorack/planar-2/, Sound On Sound Planar 2 review).
- MONOME ANSIBLE KRIA — 'polyphasic' lanes: each track's four parameter lanes (Trigger, Note, Octave, Duration) can have independent loop points, with a global sync config (None = all lanes independent / Track / All); the TIME modifier gives EACH parameter its own clock division 1–16. Loops live within 16-step grid pages, so the note:modulation ratio is bounded (~16x by division). Pattern launch is quantized: 'A cued pattern is activated when the cue clock returns to zero' (monome.org/docs/ansible/kria/).
- MONOME TELETYPE — pattern banks (4 x 64 values) are pure data read by scripts via a playhead index (P.I / P.NEXT) at ANY rate: length, rate, anchor and end behavior are all script-defined — total decoupling of automation data from note timing, at the cost of tiny capacity (64 values) (monome.org/docs/teletype/manual/).
- ABLETON LIVE (the Session-model precedent our clip player mirrors) — UNLINKED clip envelopes have their own loop brackets and length independent of the clip: 'you could have a 1 bar loop repeating, but the envelope could be controlling a plug-in parameter over 4 bars'; the audio keeps looping underneath while the longer envelope continues; envelopes are launch-relative — they restart when the clip is (re)launched (ableton.com/en/manual/clip-envelopes/, forum.ableton.com/viewtopic.php?t=223855).
- **anchorSemantics**: Every tool that supports independence makes the anchor an explicit per-track/per-pattern TOGGLE, and restart-at-launch is always the default/sync-safe option: Pyramid RELATCH ('always restarts at its beginning. It's an easy way to sync') vs FREE (keeps phase, 'tracks shift against each other') vs TRIG; Hapax TRIG setting RESTART vs FREE; Kria quantizes cued pattern activation to the cue clock returning to zero; Ableton unlinked envelopes restart with clip launch. Note these 'FREE' modes are keep-own-phase (free-running), NOT derived-from-global-transport-phase — true transport-locked anchoring essentially does not exist in this prior art. User sentiment: FREE/polymetric drift is prized for generative movement but generates predictability complaints (Pyramid users reaching for 'the calculator', fear of 'less visible limitations lurking'); the Hapax overdub thread shows performers reason launch-relatively about their automation. VERDICT: confirms the recommendation — launch-relative step-0 default, with an optional per-clip keep-phase/free mode as a later toggle (Pyramid-style), and no evidence anyone wants transport-derived phase for clip automation.
- **endBehavior**: Loop-the-automation-period is the universal default (Hapax lanes loop with the pattern; Kria lanes loop; Vector sub-sequencers loop; Ableton unlinked envelope brackets loop). One-shot exists everywhere as an explicit second mode: Pyramid TRIG run mode ('playing once... does not loop'); Planar2's loop toggle — loop ON = LFO, loop OFF = one-shot envelope/function that ends where the gesture ended (output stays at the final captured value until retriggered). Toggles are per-track (Pyramid run mode), per-recording (Planar2 loop switch), or per-pattern (Hapax TRIG setting). Hapax adds a third semantic worth copying: per-lane DEFAULT VALUES that re-assert when a pattern with no events takes over ('allows to reset a parameter after a pattern change') — i.e., 'no automation' has a defined resting value rather than whatever was last sent. VERDICT: ship loop as default + one-shot-and-hold as a per-track toggle (both have strong precedent), and consider an optional per-target default/resting value for when a clip without automation follows one with it.
- **recordingUX**: Touch-gated overdub is both validated and demanded: Elektron live-record only writes p-locks on steps passed while the knob is actually turning (untouched params preserved), and the Hapax's non-gated overdub is explicitly hated — 'if I moved 5 knobs and I don't keep on moving all 5 knobs the overdub setting just trace a line on that automation lane', with the requested fix being verbatim our design ('overdub only if a new cc message is received'). Supporting mechanics worth copying: Hapax auto-creates a lane on first incoming event and offers per-lane LOCK against re-recording; Planar2 supports punch-in/out and trigger-synced record start/length (boundary-quantized punch has hardware precedent — Hapax users also punch at end-of-pattern via the REC setting). Punch granularity: Elektron punches immediately (step-quantized), Planar2/Hapax offer boundary-synced options — our 'punch at the NOTE clip's next wrap, landing at the journey's current position' is a reasonable middle and no tool contradicts it. Position feedback for minutes-long takes is where ALL hardware fails: Hapax avoids the problem via its 32-bar cap; Pyramid users doing 256-bar journeys must hand-compute chain math; grids/LED rings show only within-page playheads. No hardware has a crash-safety commit cadence concept (all record to RAM, save on demand), so our per-note-loop Yjs commit exceeds prior art rather than conflicting with it. Our screen-side journey playhead + loop counter on the card fills a real, documented gap.
- **limitsStorage**: Two distinct storage philosophies, split by length: (A) DENSE-SAMPLED but SHORT — Hapax stores up to 1 point per clock tick at 192 ppqn (384 Hz at 120 BPM, ~2.6 ms), uninterpolated recorded data, but caps patterns at 32 bars and the project at ~1M events with a RAM monitor exposing a separate automation memory pool; Planar2 caps gestures at a flat 30 seconds. (B) SPARSE-BREAKPOINT but LONG — Vector covers hundreds of bars of modulation with only 8 steps per sub-sequencer by stretching step duration to 32 whole notes; Teletype gives 64 values read at any rate; Kria 16 steps x divisions 1-16. Nobody does automatic coarsening/decimation of recorded data — they either cap hard (30 s, 32 bars) or force sparseness structurally (8 steps). Our ~30 pts/s while-moving decimation is ~13x sparser than Hapax's 384 Hz ceiling and far denser than the sparse camp, which is a sane middle; BUT our 4000-pt/track cap (~2 min of continuous movement) undershoots the 4-minute-journey requirement (4 min x 30/s = 7200 pts). Options with precedent: raise the cap (Hapax budgets ~1M events globally and just monitors the pool), or make decimation progressively coarser for long journeys (slow journeys demonstrably need few points — Vector proves 8 breakpoints reads as musical over 256 bars).
- LESSON: Our core requirement is validated unmet demand, not speculation: the current flagship hardware sequencer (Hapax) couples automation length to clip length and its forum repeatedly asks for exactly our feature; Elektron users hack >pattern sweeps with free-running-LFO tricks.
- LESSON: Where independence exists, it is structured exactly like our design — automation as a sibling object with its own length and own clock division (Pyramid dedicated CC track, Vector sub-sequencers, Kria per-parameter lanes). Keep auto[clipIndex] as a first-class sibling with its own step count and optional own division; do not derive anything from the note clip's length.
- LESSON: ANCHOR: default launch-relative (start of journey on clip launch) — it is the sync-safe default in every tool and matches Ableton Session mental models. Reserve a per-clip 'free/keep-phase' toggle (Pyramid FREE / Hapax FREE) as a cheap later addition; skip transport-derived phase entirely — no prior art and no user demand.
- LESSON: END BEHAVIOR: loop the automation period by default; ship one-shot-and-hold-final-value as a per-track toggle (Pyramid TRIG + Planar2 loop-off precedent). Also adopt Hapax's 'default value' idea: a per-target resting value that re-asserts when a clip without automation takes over, so stale modulation doesn't stick across clip changes.
- LESSON: RECORDING: touch-gated overdub is literally the fix Hapax users beg for ('overdub only if a new cc message is received') — keep it. Add Hapax-style lane auto-create on first touched param and consider per-lane LOCK (protect a finished journey from accidental re-record) as a cheap high-value follow-up. Wrap-quantized punch-in landing at the journey's current position is consistent with Hapax end-of-pattern REC and Planar2 trigger-synced capture.
- LESSON: POSITION FEEDBACK: minutes-long takes are exactly where hardware UX collapses (32-bar caps, calculator math, page-local playheads). Put a journey-scale playhead + 'loop N of M / elapsed' counter on the card during record and playback; the launchpad keeps only arm/record/coarse-position cues — our screen split is the right division of labor.
- LESSON: STORAGE: raise or soften the 4000-pt cap — a 4-min journey at our 30 pts/s gate needs ~7200 pts. Precedented approaches: budget a large shared pool and surface usage (Hapax ~1M events + RAM monitor), and/or progressive coarsening for long journeys — long slow journeys tolerate extreme sparseness (Vector: 8 breakpoints over 256 bars). A slope-aware second-stage decimation (coarser for slow-moving segments) covers 128x lengths without ballooning Yjs docs.
- LESSON: 128x ratios have precedent only in the sparse-breakpoint camp (Vector's 1/16-note to 32-whole-note step rates give >500x; Teletype is unbounded) — dense recorded gestures top out around 30 s (Planar2) or 32 bars (Hapax). Supporting both a dense recorded head and sparse edited tail in one track format is the genuinely novel part of our design; nothing in prior art contradicts it, but nothing solves it for us either.

### Survey: Ableton Live clip envelopes (unlinked), Bitwig Studio 6 Automation Clips, Vital/Serum LFO editors, Pro Tools/Cubase automation thinning, Max function / TouchDesigner keyframe widgets
- ABLETON UNLINKED CLIP ENVELOPES are the direct precedent for our core requirement: a Session clip's automation envelope can be UNLINKED from the clip and given its own arbitrary loop length/start ('You can choose an arbitrary loop length for each envelope, including odd lengths like 3.2.1' — Ableton 12 manual, ableton.com/en/manual/clip-envelopes/). A 1-bar MIDI loop driving an 8-bar (or longer) envelope is the documented canonical use (SoundOnSound 'Using Clip Envelopes In Ableton Live'; Sonic Bloom clip-automation guide). No documented hard ratio cap — the envelope timeline is its own region, so a 128x ratio is structurally the same feature Ableton already ships.
- Each unlinked envelope gets its OWN loop braces (colored to show local loop/region settings) and its OWN Loop switch independent of the clip's Loop switch — i.e. per-envelope loop toggle, per-envelope length. Loop OFF makes the envelope play 'as a one-shot' while the sample keeps looping (Ableton 12 manual).
- BITWIG STUDIO 6 (2025) shipped 'Automation Clips': automation promoted to standalone clips in BOTH Arranger and Clip Launcher, with 'looping, independent start times, time-shifting, stretching, and clip aliases', plus a parent-child link where parent-clip edits propagate until the automation clip is directly edited, at which point they decouple (musicmanta.com/news/bitwig-studio-6; bitwig.com/stories/bitwig-studio-6-416). This validates our sibling-object auto[clipIndex] model: the industry's newest design also stores automation as a first-class object NEXT TO the note clip, not inside it.
- RECORDING PUNCH SEMANTICS (Ableton 12 manual, automation-and-editing-envelopes): Session automation recording uses TOUCH behavior for mouse (writing stops the instant you release) and LATCH for MIDI controllers — 'When you let go, recording will continue until the end of the clip's loop and then will punch out automatically.' The clip-loop boundary IS Ableton's punch-out quantum — direct precedent for our 'punch at the note clip's next wrap' proposal (theirs is punch-OUT at wrap; ours adds punch-IN at wrap).
- WRITE/OVERRIDE INDICATORS (Ableton 12 manual): an LED appears in the slider thumb when a control is automated; automation LEDs sit in control corners; manually adjusting an automated control outside recording turns the LED gray/off (automation overridden, NOT edited) until the dedicated Re-Enable Automation button is pressed or an automated clip is relaunched. Touching a knob mid-set never destroys envelope data unless automation recording is armed — the key live-safety pattern.
- THINNING/COARSENING NORMS: Pro Tools 'Smooth and Thin Data After Pass' thins breakpoints AFTER EACH automation pass, degrees none/little/some/more/most, default 'some' (soundonsound.com/techniques/write-lines; production-expert.com). Cubase 'Reduction Level' 0-100%, default 50%, applied on write-pass completion; 0% removes only repeated points (steinberg.help Automation Settings). Ableton Live 12 has a 'Simplify Envelope' command computing the optimal breakpoint set, replacing runs with lines or curved segments. Bitwig 6's Pencil translates freehand gestures into 'clean, simplified curves' at input time. Industry consensus: record dense, then simplify AT PASS/COMMIT BOUNDARIES.
- POINT-COUNT CAPS in shipping editors: Serum LFO shapes cap at 480 points, Vital at 136 per shape, excess truncated (OxyDSP/MIDIToLFO repo, which converts MIDI to LFO shapes and documents both caps). These are single-cycle shapes, so per-shape caps are small; DAW automation lanes are effectively uncapped but rely on after-pass thinning to stay editable and cheap (Pro Tools docs cite CPU load from breakpoint mass across hundreds of tracks as the motivation).
- VITAL LFO EDITOR (widely praised UX — KVR 'Lessons for Zebra3 from Vital'): double-click curve to add a point, double-click a point to delete; each segment has an 'open point' (position) plus a 'closed point' handle for SLOPE/tension; squiggly-line toggle switches straight vs curved segments; X/Y grid controls give arbitrary grid divisions (7-in-the-space-of-6 easy); paintbrush tool stamps Step/Half/Down/Up/Tri patterns per grid cell (davidmvogel.com/docs/Vital/UserGuide/Envelopes-and-LFOs; forum.vital.audio). Model = breakpoints + per-segment tension over a normalized 0..1 field — exactly our track shape.
- VITAL'S SIX LFO MODES are the cleanest taxonomy of anchor + end behavior in one menu: Trigger (retrigger on note, loop forever), Sync (locked to host tempo phase — 'subsequent notes pick up where the host tempo is in the LFO cycle'), Envelope (one-shot to end), Sustain Envelope (play to a marker then HOLD that value), Loop Point (one-shot intro then loop a tail segment), Loop Hold (loop up to a marker). Both launch-relative and transport-locked ship as user-selectable modes, as do loop-vs-hold endings.
- BITWIG 6 automation editor: per-point Curvature (slope to next point) editable numerically in the Inspector; ALT-drag on a segment center bends it; 'Spread' (humanize) and 'Hold' (flat-value lock) behaviors; new Spray Can paints held points at the current grid interval (bitwig.com userguide/release notes; musicmanta).
- ABLETON EDITOR UX BASELINE: two explicit modes — Draw Mode (stepped, grid-quantized; grid can be hidden for freehand) vs breakpoint mode (click segment to add, single-click a breakpoint to delete, Alt-drag segment to curve it, Alt-double-click to straighten, Shift for fine values, snap to grid bypassable) (Ableton 12 manual, both chapters).
- MAX/TOUCHDESIGNER: Max's 'function' object is the classic breakpoint-envelope widget (click to add, drag, per-segment curve via curve~), but Cycling '74 forum threads show users rolling their own editors because built-in curve editing is basic — not a UX model to copy. TouchDesigner's Animation COMP/Keyframe CHOP is a full offline keyframe editor sampled at a chosen rate — a production tool, not a live-performance surface (docs.derivative.ca/Keyframe_CHOP).
- CABLEGUYS/SHAPERBOX (transport-locked school): LFOs sync to the host timeline by default; they had to ADD MIDI Trigger ('On (1-Shot)') and Audio Trigger modes because timeline lock frustrates live/rhythmic use, and PDC makes timeline-synced plugins misalign in Live/Logic (cableguys.com/support). Evidence that transport-locking a performance envelope generates workaround demand.
- Ableton's 'Lock Envelopes' switch is an ARRANGEMENT editing affordance (keep envelopes at song position while moving clips), not a Session playback mode — Session clip envelopes are launch-relative, full stop; forum threads ('Reset clip envelopes on start', t=225195) discuss reset nuances (envelopes reset on Stop, not on retrigger-quantize edge cases) but nobody gets transport-phase clip envelopes in Live.
- **anchorSemantics**: LAUNCH-RELATIVE CONFIRMED as the clip-launcher convention. Every clip-attached automation system surveyed is launch-relative: Ableton Session clip envelopes (linked AND unlinked) start from the envelope's start position when the clip launches — there is no transport-phase option for Session envelopes at all; Bitwig 6 Automation Clips are launcher clips and launch like any clip. Transport-locked is the convention for a DIFFERENT category: arrangement/timeline automation and insert-effect LFOs (ShaperBox/LFOTool sync to host timeline by default) — and notably that school accumulated user friction: Cableguys added MIDI 1-Shot and Audio Trigger modes because timeline-locked phase fights live performance, and PDC breaks timeline sync in Live/Logic. The reverse complaint exists but is milder: Ableton users occasionally want continuity across retriggers (a relaunch restarts a long unlinked envelope from 0; the community workaround is Legato-mode clip switching to preserve play position). Vital ships BOTH as modes (Trigger = launch-relative, Sync = transport-phase) one dropdown apart, proving the toggle is cheap to expose later. Verdict: launch-relative at step 0 is the right default and matches all clip-launcher prior art; reserve a per-clip 'sync/transport-phase' mode as a post-v1 toggle (Vital-style), and note the retrigger-restarts-the-journey consequence in UX (a relaunch = journey restart, which performers expect from Ableton).
- **endBehavior**: Both endings ship in prior art, toggled PER ENVELOPE. Ableton: each unlinked clip envelope has its own Loop switch independent of the clip's — Loop ON loops the envelope at its own length; Loop OFF plays it 'as a one-shot' while the clip keeps looping (manual); the canonical one-shot use case is a fade-out spanning many clip repetitions, which only works if the final value HOLDS after the envelope ends (hold-at-end is the observed Live behavior; the manual doesn't state it in words but the fade-out use case depends on it). Vital makes the menu explicit: Envelope (one-shot), Sustain Envelope (play-then-hold at a marker), Loop Point/Loop Hold (partial-loop variants), Trigger (full loop). Bitwig automation clips 'support looping' as a clip property. Recommendation confirmed with one amendment: default LOOP (matches Trigger-mode LFO expectations and our 'automation as journey' pitch), but ship the ONE-SHOT-AND-HOLD toggle in v1, not later — it's a per-envelope boolean in every tool surveyed, it's what makes 'slow build over 4 minutes then stay there' (the marquee 128x use case) actually usable, and Ableton demonstrates the pair (own loop brace + own Loop switch) is the complete feature. Vital's Loop Point (one-shot intro, then loop the tail) is a nice-to-have later, cheap once loop-region markers exist.
- **recordingUX**: Punch granularity: Ableton already uses the CLIP-LOOP BOUNDARY as its punch quantum — MIDI-controller (latch) automation recording 'will continue until the end of the clip's loop and then will punch out automatically', while mouse input punches out instantly on release (touch). This directly supports our proposal to punch at the NOTE clip's next wrap; Ableton lands the punch-OUT there, we'd also quantize punch-IN there — a defensible extension since our journey position is only meaningful modulo the note-loop grid. Recommend offering both semantics per input: instant-on-touch write for on-screen (mouse/touch = Touch mode), wrap-quantized punch-out for hardware knobs (Latch mode) — this is exactly Live's split and users know it. Commit cadence: no tool commits mid-pass; Pro Tools smooths-and-thins AFTER EACH PASS and Cubase applies Reduction Level on pass completion — the pass/loop boundary is the industry's commit-and-coarsen point, which endorses our per-note-loop Yjs commit for crash safety (and is where our decimation/coarsen step should run). Position feedback during minutes-long takes: hardware gives almost nothing — Live/Launchpad show only a pulsing red record pad and the clip-slot progress pie; ALL position-in-take feedback lives on screen: playhead line moving through the envelope editor, red/tinted lane while writing, per-control LED (writing) vs gray LED (overriding, not writing). So our split is correct: launchpad = arm/record-state/coarse cues only; the card shows the moving playhead in the journey, a 'writing' tint on touched tracks only (touch-gated overdub means untouched tracks visibly keep their old curve — mirror Live's red-vs-gray LED distinction per track), plus a journey-position counter (bar N of M / mm:ss) since a 4-minute take exceeds any visible pie.
- **limitsStorage**: Prior-art numbers: Serum caps an LFO shape at 480 points, Vital at 136 (single-cycle shapes — small by design; excess truncated). DAW lanes are effectively uncapped but universally COARSEN AT PASS BOUNDARIES: Pro Tools 'Smooth and Thin Data After Pass' (degrees none→most, default 'some'; motivated by editability and CPU across hundreds of tracks), Cubase Reduction Level 0–100% default 50% ('reduces the data amount significantly without touching the sound result'), Ableton's Simplify Envelope command (optimal breakpoint set, straight or curved replacements), Bitwig 6's Pencil simplifying freehand strokes at input time. Our ~30 pts/s record-time decimation gate is DENSER than what survives in any DAW after thinning — human gestures at ~50% Cubase reduction land around a few points/s except at direction changes. Recommendation: keep the 30 pts/s live gate (cheap, bounds worst case), then run a Ramer-Douglas-Peucker-style simplify pass at each note-loop commit (the Pro Tools model) with an error tolerance ~0.5–1% of the 0..1 range; that typically cuts continuous-wiggle data 5–10x, so the 4000/track cap stops meaning '2 minutes of movement' and starts meaning '10+ minutes of surviving gesture detail'. Keep 4000 as the hard cap but make the enforcement a progressive coarsen (raise RDP epsilon until under cap) rather than a truncation — truncation is the one behavior prior art (Serum/Vital import) shows and it reads as data loss. Per-segment tension (Bitwig curvature / Vital slope handle) also REDUCES point demand: one curved segment replaces dozens of linear samples, which is exactly what Ableton's Simplify exploits.
- LESSON: (a) Minimal v1 editor: Ableton proves the floor is breakpoint mode, not draw mode — view the envelope with its own loop brace + moving playhead, click-segment-to-add-breakpoint, click-breakpoint-to-delete, drag with grid snap (mod-key to bypass), per-track clear. Freehand draw is NOT needed day 1: in our design RECORDING is the primary input (touch-gated overdub), same as Live where most clip automation is performed then tidied as breakpoints. Add Vital-style double-click add/delete as the discoverable gesture. Draw/paint (grid-stepped) is the best v2 candidate, not v1.
- LESSON: (b) Data model: breakpoint + per-segment tension over normalized 0..1 is the consensus (Vital slope handles, Bitwig per-point Curvature with numeric Inspector entry, Ableton Alt-drag curves, LFOTool point+tension). Ship linear-only rendering day 1 if needed, but put a tension scalar (default 0 = linear) on the segment in the Yjs schema NOW — every surveyed tool retrofitted curves and it churned their formats; step-value is not a separate model, it's breakpoints + Y-grid + a paint tool (Vital), so don't build a parallel step representation.
- LESSON: (c) Showing a 4-min journey against a 2s clip: no surveyed tool solves this well on one strip — Ableton just gives the unlinked envelope its own ruler/zoom with colored loop braces. Build: (1) a full-journey OVERVIEW strip (decimated polyline + playhead dot + loop/region brace), (2) a zoomed main editor auto-following the playhead during playback/record, (3) note-clip WRAP TICKS as the dominant gridline (every 2s wrap = one tick; 128 ticks make the ratio legible and give the punch-in quantum a visual anchor). The overview strip doubles as the scrub/zoom control (drag a window on it) — the standard DAW minimap pattern.
- LESSON: (d) Live-performance safety — copy Ableton's exact contract: touching a control mid-set NEVER edits stored automation unless record is armed; it temporarily OVERRIDES (gray LED) with a one-tap Re-Enable Automation to snap back to the envelope. Map to us: card knob-touch while not recording = transient override (our CV-modulation-not-Y.Doc rule already enforces the no-write part), per-track re-enable affordance, and destructive editor ops (delete/clear/drag) gated behind an explicit edit mode on the card — single-click-delete on breakpoints (Ableton) is too dangerous mid-set without an edit-mode gate; multiplayer Yjs undo covers the rest.
- LESSON: ANCHOR decision: confirm launch-relative step-0 (all clip-launcher prior art; transport-locked school generated workaround demand). Design the auto-position as clipLaunchTime-derived so a later per-clip 'Sync' mode (Vital-style transport-phase) is a pure read-path toggle.
- LESSON: END decision: default loop, but promote one-shot-and-hold to v1 as a per-envelope boolean (Ableton per-envelope Loop switch; Vital Envelope/Sustain-Envelope modes) — the 4-minute build-and-hold is the marquee 128x story and it needs hold-at-end.
- LESSON: RECORD decision: our wrap-quantized punch is a legitimate extension of Live's latch punch-out-at-loop-end; keep instant Touch-style write for on-screen gestures, wrap-quantized latch for hardware. Commit + RDP-coarsen at each note-loop wrap = the Pro Tools after-pass model; show per-track writing-vs-overriding state (red vs gray) since touch-gating means tracks differ mid-take.
- LESSON: STORAGE decision: 30 pts/s gate is fine; add commit-time simplify (RDP epsilon ~0.5-1% of range, Cubase-default-equivalent) so the 4000 cap covers 10+ min of gesture; enforce the cap by progressive coarsening, never truncation; tension segments are a storage optimization, not just cosmetics.
- LESSON: Bitwig 6's parent-child decouple rule (parent clip edits propagate to the automation clip until it's directly edited) is worth stealing later for clip copy/duplicate semantics: duplicating a note clip should carry auto[clipIndex] as a linked copy that decouples on first edit.
