§1 — WHAT THE MODULE IS FOR

The verb is DRAW. A tiny Windows-95 Paint whose canvas IS the output frame, 1:1 at engine resolution: 9 tools (pencil/brush/eraser/fill/pick/line/rect/ellipse/text), the 28-colour Win95 swatch grid (2×14, left-click FG / right-click BG), SIZE slider, FILL toggle, UNDO/CLEAR. The drawing is a Y.Doc-synced ordered op log (node.data.ops, PaintOp[]) replayed deterministically on mount/remote-edit (painter-draw.ts, pure + unit-tested), so every collaborator paints the same picture. Tool/colour/size are LOCAL per collaborator — only the drawing syncs.

§2.3 The one mechanism that does NOT survive as-is: card-mounted replay-and-push

the #1720 gap, painter edition

The card owns: (a) the 2D canvas the op log is replayed onto, and (b) the one-time setPaintCanvas bind. Under the shipping shell an un-promoted painter renders a placeholder tile and the card mounts only in the dock — so a SAVED rack with a painting shows the WHITE PLACEHOLDER on load until someone expands the pane. Textmarquee already fixed exactly this class by moving render-and-push to node-lifetime $lib/ui/media/extras-producers (#1720: “the node shows your text with no card mounted”). The face PR must port painter’s replay-and-push onto the same extras-producers seam — a node-lifetime producer that replays node.data.ops into an offscreen canvas and binds it, with the body’s interactive canvas becoming a second consumer of the same op log, not the producer of the frame. This is the skifree/#1531 registry pattern the 08-24 face-plan already prescribes: use the existing seam, do not invent a mechanism.

§5.1 Bands / width

Zero bands (no ranked keys → no band at all, not even an unlabelled one). Width IS earned — by the picture: the body canvas at a legible editing size (~480 px wide at 4:3) is a “live picture” earner in the compact ruling’s own list. Slack ≈ 0 by construction (the widest element is the canvas). No width exemption.

§6.2 The component

$lib/ui/modules/painter/shell-extension.ts → { fullViewBody: PainterEditorBody }. Contents, top to bottom: toolbar (9 tools + size + fill + text stamp + UNDO/CLEAR) · the drawing canvas (interactive, replaying the shared op log; commits through the same painter-draw.ts helpers the card uses — one write seam, two mounts, the livecode/DX7 shared-action pattern) · FG/BG chip + the 28-swatch palette. The engine frame keeps coming from the node-lifetime producer (§2.3); the body canvas is a synchronized VIEW that also accepts input, so closing the pane never blanks the output.

§6.4 Screen switch — required (video ∩ STRICT_FACES), with a wrinkle

The video-face-screen-source gate will demand a screen switch over node.data.previewCollapsed. For painter the “preview” IS the editor: collapsing it removes the ability to draw until re-expanded. That is acceptable — OFF skips the PAINT, never the producer (the op log and output keep living), and a collapsed painter is exactly “I am projecting this, stop spending dock pixels on it.” The switch overlays the canvas corner on a translucent backplate (the anti-pattern is a stacked chrome row). Do NOT add painter to NO_SCREEN_SWITCH: that list’s one entry is videoOut (“videoOut IS the screen”), and painter’s canvas is an EDITOR first — the switch has a real meaning here, so the exemption argument fails.
