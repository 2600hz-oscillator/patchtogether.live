§0.1 The inventory why is stale — read the card, never the why

The inventory says “a getUserMedia stream the card starts and stops with its own lifetime.” That was true when written and is FALSE on this tree: #1590 (from the #1583 audit) moved stream + status + reconciler into nodeAudioInput, keyed by NODE id, swept on graph lifetime. AudioinCard’s own header: “inState / errorMsg / liveChannels are DERIVED from the node-keyed registry, not card-local $state (#1590) … The registry is the one home for both the resource and the status that describes it.” This is the standing wave-7 instruction (“3 confirmed-false whys in wave 7 alone”) landing a fourth time. The spec below builds on the registry, and the PR body should note the stale why for the owner (the inventory file edit rides the face PR: disposition flips to generic-face, blockers empty — forced by the inventory test the moment a face is authored).

§1 — WHAT THE MODULE IS FOR

The verb is BIND. Bring system audio into the patch: pick an audioinput device, grant permission, and the module exposes the live capture as a stereo pair (audio_l_out/audio_r_out; mono sources fan out L=R, stereo devices split through a ChannelSplitter). One knob: post-source gain. Permission is requested only on an explicit user gesture — loading a patch never pops a mic prompt. The interesting state (idle / requesting / streaming / permission-denied / no-inputs-found / device-in-use / unsupported / error) is SERVICE state, browser-instance-local, deliberately not in the graph.

§4 — THE LANE PICTURE

domain === 'audio' → no free video thumb. But audioIn HAS a real type:'audio' output pair, so primaryAudioOutPortId resolves and glyph: 'meter' binds live-audio honestly — a VU of the actual captured signal. This is the one glyph that answers the module’s only performance question (“is my mic live and how hot?”) with data that cannot lie: silence reads empty, clipping reads full. The bluebox ruling applies (the meter is a genuine hazard signal — a hot line-in at gain 2 can clip). Declaring the meter moves the lane to the glyph-bearing cap column (compact cap 3→2): gain + music-mode fit; the tile’s device/enable affordances live in tileBody, which appends BELOW the ranked cells by design.

§6 — THE BODY: face.extension: 'audioIn', slots fullViewBody + tileBody

§6.1 Why not a shell selector cell — the settled argument, cited not re-litigated

The device roster is SERVICE state (a live enumerateDevices answer), not node state — no selector cell projects it (the inventory’s own words, and the one clause of its why that is still true). The wave-4 “give env a read seam” ask is a disproven blocker, refuted on three independent axes (BINDERS.md §1/§9: ShellCellEnv.engine has no read; reach; ownership). The body resolves the roster itself — module-owned code may import what it needs (getActiveEngine() where an engine read is wanted, navigator.mediaDevices + the registry here). Do not re-propose the env change.

§6.3 Status without state-words — the five failure states as lamps

Eight states collapse to three lamps with STATIC captions (a caption that changes with state is refused — the Connect/Re-connect discriminator):

lamp (static caption)lit whentonedetail → aria-label/title (never painted)
CAPTUREstreamingaccent“streaming, stereo, ES-9” / “streaming, mono (L=R)”
PERMISSIONpermission-denied / unsupportedwarnthe exact failure prose the card’s error line carried
DEVICEno-inputs-found / device-in-use / errorwarnper-state prose (“another tab holds the microphone”)

requesting is transient and paints as the CAPTURE lamp unlit + the ENABLE button disabled — not a fourth lamp. There is deliberately NO green “connected to hardware” promise beyond what the meter proves: the chromaconsole open-loop ruling (“a reassuring indicator would be a lie”) — here the meter closes the loop honestly, so CAPTURE lit + meter moving is the truth, and CAPTURE lit + meter flat is itself diagnostic (device muted at the OS).
