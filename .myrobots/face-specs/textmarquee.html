§1 — WHAT THE MODULE IS FOR

The verb is TYPE (then fly it around). A styled paragraph (system fonts, per-run colour, B/I/U, align, font family + size, one layer background) is serialized to a rich-text MODEL in node.data.richText, rasterized offscreen to real system glyphs, uploaded as a texture, and drawn as ONE ribbon whose position (PosX/PosY) and crawl (ScrlX/ScrlY, 0.5 = static) are the four params — each with a matching bipolar CV input calibrated so a ±1 LFO sweeps fully off one edge, across, and back. Everything outside the ribbon’s block is layer black. A fresh node shows the built-in “textmarquee” placeholder.

§6 — THE BODY: face.extension: 'textmarquee', slot fullViewBody

§6.1 Why not a cell — the ladder, walked

rungrefusal
entry cell (the ONE cell permitted to paint text at rest, ‘authored-entry’)it is a TYPED-ENTRY FIELD for a short string — a name, a URL. A multi-paragraph rich-text model with per-run styling and selection-scoped formatting is “beyond a short-text field” (the inventory’s own words). Squeezing the model through an entry cell loses runs, alignment and selection semantics — a parity loss, refused
panel cellthe editor needs the toolbar + font controls + bg colour AROUND the editable region — an editor suite, not one picture-you-edit
editorSurface slotUNWIRED; fullViewBody gives the same real estate wired today (the painter argument, verbatim)
fullViewBodyTAKEN — preview on top, editor + toolbar below, one component

§6.2 The component

$lib/ui/modules/textmarquee/shell-extension.ts → { fullViewBody: TextmarqueeEditorBody }. Contents: the live preview (downscaled OUT layer, SCREEN switch overlaid) · the toolbar (align/B/I/U/colour/font/size/bg) · the contenteditable region (same serialize seam + MAX_CHARS truncation + selection preservation) · the “TYPE TEXT…” empty badge. The producer (#1720) keeps owning rasterize-and-push; the body only edits the MODEL — exactly the card’s split, so the body is small and the split is already proven.

§8 — TYPED-ENTRY GATE — the genuine case, and the routes

TRIPS, and is SUPPOSED to. textmarquee is a named positive control of the instrument, and the standing wave-7 ruling preserves exactly this module’s right to stay blocked: “the blocker keeps meaning what it says, for modules that genuinely need free typed text in a lane.” The routes:

routecostverdict
(a) strip typed entry from the legacy cardabsurd here — the editor IS the module; there is nothing to strip torefused
(b) narrow the gate’s subject to the FACE’s own templatea CI-gate edit — owner-routed (no-CI-changes ruling). NOTE: unlike painter, this route is textmarquee’s only promotion path that keeps the editor, and the gate’s own positive-control list would need re-anchoring (it names textmarquee)report to owner; the honest framing is “extend the gate to distinguish a bespoke-surface BODY editor from a lane cell” — the blocker was always about lane cells
(c) do not promote yettextmarquee stays a placeholder tile; its four CV-driven knobs stay unreachable in the shipping shell — a real cost, since motion is CV-performable today only via cablesthe default until the owner rules; this spec makes (b)’s case concrete
owner decision requiredWhether a text-EDITING fullViewBody is an acceptable escape from the typed-entry blocker is precedent-setting (only file-input and read-only-text bodies ship today). This spec designs the surface so the decision is about the RULE, not about missing design work.
