RASTERIZE — the lane-glyph decision, drawn

Mockup only. Nothing here is implemented. rasterize has been faced since #2001. The one question #2160 re-opened is whether its lane tile should now carry a picture. Three options were legal to declare; all three are drawn below. Only the left one ships, and it is what ships today.

Three ranked cells — the three controls that change the picture. Strictly more than the placeholder an un-promoted module shows, and every pixel of the tile is doing work.

The raster itself reaches the player through fullViewBody at the dock, where it has 480×360 to be legible in.

OPTION BREFUSED

A trace glyph on thru

glyph: 'scope' → {kind:'live-audio', portId:'thru'}
rasterize
Samp/F

It is LIVE and it is green on every gate. rasterize declares a type:'audio' output, so primaryAudioOutPortId resolves and the dead-glyph clause never fires.

⚠ And it says nothing. thru IS inGain — bit-exactly this module’s INPUT — so the trace is invariant to all four controls. It moves with the music, looks healthy, and is blind. rasterize.ts:173-191 already calls this “the first that resolves LIVE AND IS STILL BLIND, which no gate looks for”. It would also be a live moving surface in the compact VRT baseline.

OPTION C · NEW SINCE #2160REFUSED

glyph: 'algorithm' → {kind:'algorithm', layoutSource:'rasterize', paramId:null}

(no caption)
Samp/F

Also live-kind, also green. The extension arm at shell-glyph-live.ts:156-159 resolves it because the def already declares extension:'rasterize'.

⚠ And it is a CONSTANT. ModuleShell.svelte:462 hardcodes topologyValue to 0 when paramId is null, :473 returns '' for the caption, and ShellExtensionGlyphProps carries no nodeId. Every node in every rack renders the same SVG, forever. Its precedence is also tier-dependent: at 'full' it is dropped whenever the plate is busy (“Ranked controls outrank the glyph”), and at 'compact' — the tile drawn here — it paints unconditionally and takes the space from the cells beside it. Absent where detail is wanted; present where the tile can least afford it.

⚠ NOTE WHAT THE TWO REFUSED TILES HAVE IN COMMON. In both, the glyph pushed the WRAP cell out of the tile — the one control whose two states are this module’s two looks, and the one whose names (WRAP/CLAMP) exist nowhere else. A tile is a fixed budget; a picture that cannot vary is spending it on nothing.

THE GENERAL FORM, FOR THE WHOLE FIVE-MODULE COHORT. #2160 removed a refusal; it did not add a data path — shell-glyph-live.ts:101-103 says so in its own words. Until ShellExtensionGlyphProps gains a nodeId the way ShellExtensionFullViewBodyProps already has one, no module in the cohort gains an informative lane picture from it. rasterize is where that is cheapest to check, because it is the only cohort member already faced — the experiment is one word. The escalation belongs to scope, which would be the best adopter of the fixed prop. See ../scope/spec.md §12.3.
⚠ AND THE DEF’S OWN COMMENT IS NOW WRONG. rasterize.ts:188-191 still says the picture “matches no glyph kind”. It matches one. The refusal changed from no kind fits to the kind that fits carries no data, and the comment has to change with it or the next reader re-derives the widening from scratch and may reach the opposite conclusion. spec.md §2.3 carries the replacement text.
